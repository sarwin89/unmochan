# Findings: correctness issues, gaps and their resolution

This is the review log for the audit of the unfolding mathematics and of the
implementation.  Each entry states the problem, the observable consequence, and
what was done about it.  The mathematical statements referenced by name are
machine-checked Lean theorems; see `docs/formal-model.md` for the dictionary
between them and the Python API.

---

## 1. Bugs fixed

### 1.1 The wavefunction file's own k-point representative was ignored (VASP)

**Severity: high — silently wrong weights.**

`compute_weights_from_wavecar` passed the k-point taken from the *k-map* as
`folded_supercell_kpoint`, while the plane-wave (G-vector) list it used was
generated by, and indexed against, the representative stored *in the WAVECAR*.

The matching condition only depends on the physical vectors `K + G`
(`UnfoldLab.pwMatches_of_add_eq`), so if the two representatives differ by a
reciprocal lattice vector `m` — e.g. `0.75` in the k-map versus `-0.25` in the
file, which is the same k-point — the whole G-list is offset by `m` relative to
the k-point it is compared with.  Every weight at that k-point is then computed
from the wrong subset of plane waves.  Nothing in the output flags this: the
weights still lie in `[0, 1]`.

*Fix:* the reader now uses the WAVECAR's own representative for the matching
and additionally requires it to agree with the k-map modulo 1, raising a clear
error otherwise (a genuine mismatch means the k-path and the WAVECAR are not
the same calculation, or are ordered differently).

### 1.2 The same problem for Quantum ESPRESSO, previously undetectable

QE's `wfc*.dat` / `wfc*.hdf5` files store the k-point (`xk`) they belong to, and
their Miller indices are indexed against it — exactly as for the WAVECAR.  The
reader parsed the header record but *discarded* `xk`, so the check of 1.1 could
not be performed at all and the caller was silently trusted.

*Fix:* `xk` is now retained (`BinaryHeader.xk`, `read_xk_dat`, `read_xk_hdf5`).
`compute_weights_from_qe_save` takes an optional `lattice_alat` (QE's `at`
matrix, i.e. the direct lattice in units of `alat`); when given, the file's
`xk` is converted to fractional coordinates, cross-checked against the k-map
modulo 1, and then used as the representative for the matching.  Without a
lattice the conversion from QE's Cartesian `2π/alat` units is impossible, so
the check is skipped and the old behaviour is preserved.

`tests/test_qe_wfc_kpoints.py` builds synthetic `wfc1.dat` and `wfc1.hdf5`
files and covers both the accepted and the rejected case.

### 1.3 Band-path distances were measured in fractional coordinates

**Severity: medium — distorted plots, wrong band velocities.**

`interpolate_path` accumulated `|Δk_frac|`, the Euclidean norm of the
*fractional* difference.  That is proportional to physical distance only for a
cubic reciprocal lattice.  For a hexagonal cell the Γ–K and Γ–M segments come
out with the wrong relative lengths, so any slope read off the plot is wrong.

*Fix:* `interpolate_path` / `build_qe_path` accept a `primitive_lattice` and
then accumulate the Cartesian distance `|Δk_frac · B|` with `B = 2π inv(A)ᵀ`;
`read_path_json` picks up an optional `"primitive_lattice"` entry.  The
fractional behaviour remains the default so existing path files keep working.

### 1.4 Valley regions were spheres in fractional coordinates

**Severity: medium — wrong k-point classification for non-cubic cells.**

`ValleyDefinition.contains` computed `|Δ − rint(Δ)|` in fractional coordinates.
Two independent problems:

* the metric is fractional, so a "sphere of radius r" is an ellipsoid of the
  wrong shape in reciprocal space;
* `rint` is not the minimum image for a non-orthogonal metric.  For a hexagonal
  reciprocal lattice and `Δ = (0.4, 0.4, 0)` the reduced vector is **not** the
  shortest image — `(−0.6, 0.4, 0)` is shorter — so a k-point can be reported
  outside a valley it is actually inside.

*Fix:* new `minimum_image_distance(delta_frac, reciprocal_lattice=None)` which
minimises the Cartesian length over a ±2 shell of reciprocal-lattice
translations; `contains` and the new `distance_to` accept an optional
`reciprocal_lattice`.  `tests/test_valleys.py` checks the hexagonal case against
a brute-force ±4 search.

### 1.5 CLI usage errors escaped as tracebacks

`_click_exception_classes` only looked at the top-level `click` package, but
Typer vendors its own copy; a usage error raised through Typer therefore
propagated as an unhandled exception instead of a usage message.  Fixed by also
collecting the exception classes from Typer's vendored click.  This was the one
test failing at the start of the audit.

## 2. Mathematical / numerical weaknesses addressed

### 2.1 The G-matching test was a floating-point rounding test

The matcher used to compute `(K + G) · inv(T)ᵀ − k` in floating point and accept
the plane wave when every component was within `atol` of an integer.  Two
consequences: the answer depends on a tolerance, and `np.linalg.inv` of an
integer matrix with a large determinant loses precision.

`UnfoldLab.mem_range_mulVec_iff_adjugate` gives an exact criterion:
`v ∈ T·ℤ³` iff `det T` divides every component of `adj(T)·v`.  Both `det` and
`adj` of a 3×3 integer matrix are integer polynomials in the entries, so the
whole test is exact integer arithmetic.

*Fix:* `integer_det3`, `integer_adjugate3` and the rewritten `matching_g_mask`
implement exactly that; `tol` now only validates that the *inputs* are integral.
`tests/test_exact_matching.py` checks agreement with the float reference on
diagonal, non-diagonal and sheared transformations.

### 2.2 A tolerance of ≥ 0.5 accepts everything

Any "is this an integer within `atol`" test is **vacuously true for every real
number** once `atol ≥ 1/2` — formalized as `UnfoldLab.roundTest_of_half_le`.
A user raising a tolerance to make a stubborn check pass therefore disables the
check completely rather than loosening it.

*Fix:* `check_atol` rejects `atol ≥ MAX_MEANINGFUL_ATOL = 0.5` at every entry
point that consumes a tolerance.

### 2.3 `max_band_sum` looks like the sum rule but is not

`WeightDiagnostics.max_band_sum` sums weights *over bands at one k-point*.  The
sum rule of band unfolding is a sum over the **fiber of primitive k-points at a
fixed band** (`UnfoldLab.IsFiberRepr.sum_weight_eq_one`): the `|det T|`
primitive k-points folding onto one supercell k-point carry weights summing to
one.  `max_band_sum` has no reason to be `1`, and reading it as a validity
check is misleading.

*Fix:* the docstring says so explicitly, and a real diagnostic was added:
`diagnose_fiber_sum_rule` groups the k-map by supercell k-point, checks that
each group is a complete fiber of size `|det T|`, and reports the deviation of
each fiber sum from one.  `compute_backend_weights` now emits a warning when a
fiber sum deviates measurably.  Note that the diagnostic is only meaningful for
a k-map that covers whole fibers — a band-structure path usually does not, which
is why it warns rather than raises.

### 2.4 Float determinants for an integer matrix

`np.linalg.det` on the transformation matrix returns e.g. `5.999999999999998`
for a determinant of 6, and the code compared it against integers and used it as
a divisor.  Determinant and adjugate are now computed exactly in integers, and
`SupercellTransformation.inverse` is built from `adj(T)/det(T)`.

### 2.5 No cross-check between the supercell size and the transformation

Nothing verified that the supplied `T` is consistent with the structures it is
supposed to relate.  `check_supercell_consistency` now compares `|det T|` with
the cell-volume ratio (`UnfoldLab.abs_det_supercell`) and with the site-count
ratio, which catches the common mistakes of a transposed or wrongly signed `T`
and of pairing a structure with the wrong supercell.

### 2.6 Broadening was not checked to conserve spectral weight

`∫ A(E) dE = Σ_j w_j` holds for any normalized kernel
(`UnfoldLab.integral_spectralFunction`, with the Gaussian and Lorentzian
normalizations proved separately).  This is the cheapest end-to-end test of the
spectral pipeline and it was absent; it is now in `tests/test_spectral.py` for
both kernels, and an unknown kernel name is rejected up front instead of
silently falling through.

## 3. Performance

* `matching_g_mask` is a single `(n_g, 3) @ (3, 3)` integer product followed by
  a modulus, instead of a per-G-vector float solve.
* `weights_from_coefficients` replaces `abs(c)**2` (which computes a square root
  and then squares it) by `c.real² + c.imag²`, and contracts bands against the
  mask with one matrix–vector product rather than a Python loop over bands.
* `compute_weights_from_coefficient_table` parses the table once and then works
  per k-point on contiguous slices; previously the table was re-scanned for
  every k-point.
* `spectral_function` hoists the kernel constants out of the loop and evaluates
  the kernel on the whole energy grid at once.

## 4. Remaining gaps and caveats

These are documented rather than fixed, because fixing them needs either more
input data than the library currently receives or a physical decision by the
user.

1. **Plane-wave-only normalization (PAW/USPP).**  Weights are computed from the
   plane-wave coefficients alone.  For PAW or ultrasoft calculations the
   augmentation charge inside the spheres is not represented, so the weights are
   those of the pseudo wavefunction.  Sums over a fiber will still be one
   (the pseudo wavefunction is normalized in the plane-wave basis), so the sum
   rule does **not** detect this; the systematic error is in the distribution of
   weight between k-points, and it is largest for localized `d`/`f` states.

2. **QE k-point check needs `alat`.**  The consistency check of §1.2 is only
   active when the caller supplies the direct lattice in `alat` units.  The
   library does not infer it from the `pw.x` input, because the relation between
   `alat` and the cell depends on `ibrav`, `celldm`, `A`, and on the units of
   `CELL_PARAMETERS`; guessing it would replace a missing check with a wrong
   one.

3. **Γ-only wavefunctions are rejected, not supported.**  *(Resolved in §6.2.)*  Both readers refuse
   `gamma_only` files.  Supporting them means reconstructing the `−G` half of
   the basis; until that is implemented, refusing is the safe behaviour.

4. **No symmetry reduction.**  *(Resolved in §6.3.)*  The k-map must list every k-point explicitly; the
   readers assume the wavefunction files are in the same order.  A calculation
   run with symmetry reduction of the k-mesh will have fewer files than the map
   and is rejected by the count check, but the library cannot expand the
   irreducible wedge for the user.

5. **Spin/spinor components are summed incoherently.**  *(Resolved in §6.4.)*  Multiple polarization
   components are treated as independent contributions to the same norm.  That
   is correct for the total weight, but it means no spin-resolved unfolded
   weight is available.

6. **The fiber sum-rule diagnostic needs complete fibers.**  On a band-structure
   path only a few supercell k-points have all `|det T|` preimages present, so
   the diagnostic is informative for meshes and mostly silent for paths.

## 6. Second pass

A follow-up review closed four of the gaps of §4 and fixed two further reader
bugs.  Everything below is covered by tests, and the mathematics behind each
item is machine-checked in `lean-proofs/RequestProject/Unfolding/` (see
`docs/formal-model.md`).

### 6.1 The minimum-image search is now certified, not heuristic

`minimum_image_distance` used to search a fixed neighbour box.  No fixed box is
correct for every cell shape, and componentwise `rint` reduction is not the
minimum image for a non-orthogonal cell
(`UnfoldLab.exists_shorter_image_than_reduced`).

The search now grows the box until a **stopping certificate** holds: with
`sigma = |det B| / ||adj B||_F` a certified lower bound on the length of a
lattice translation per unit coefficient (`lattice_growth_constant`,
`UnfoldLab.abs_det_mul_euclidLen_le`), a translation outside a box of radius `r`
is at least `sigma * (r + 1 - ||delta||)` away, so once the best distance found
inside the box is below that value the answer is provably the global minimum
(`UnfoldLab.minimum_image_box_exact_frac`).  If no certificate is reached within
`MAX_IMAGE_SEARCH_RADIUS` the function raises instead of returning an
uncertified number.

### 6.2 Γ-only wavefunctions are supported

Both readers now expand the stored half basis by time reversal
(`c_{-G} = conj(c_G)`, `unfoldlab.core.gamma.expand_gamma_half_basis`) before
unfolding.  This is necessary, not cosmetic: unfolding the stored half directly
gives a *different* weight (`UnfoldLab.exists_half_basis_weight_ne` exhibits a
case where the correct answer is 1/3 and the half-basis answer 1/2).

For VASP the half-space convention is a property of the build, not of the file.
Both conventions in circulation are supported through `gamma_half`, and the rule
itself ("keep the origin, otherwise keep the vector whose first nonzero
component along the axis order is positive") is proved to select exactly one
member of each pair, with the sphere recovered exactly on expansion
(`UnfoldLab.inHalfSpace_neg_iff`,
`UnfoldLab.gammaExpand_filter_inHalfSpace`).  When the two conventions give the
same stored count the file cannot be told apart and `gamma_half` must be set by
hand; this is documented on `WavecarReader`.

### 6.3 Symmetry-reduced wavefunction sets can be unfolded

Passing `operations` (point-group matrices in primitive reciprocal coordinates,
`--symmetry` on the command line) drops the requirement that the WAVECAR hold
exactly the k-points of the k-map in the same order.  Each requested primitive
k-point is matched to whichever stored k-point reaches it under one of the
operations, and unfolded against that file after the corresponding rotation.

No plane-wave coefficients are touched: the weights are equivariant,
`w(S_pc k ; S_sc K) = w(k ; K)` with the *stored, unrotated* list
(`UnfoldLab.weight_symmetry`), and the rotated primitive k-point folds exactly
onto the stored one (`UnfoldLab.fold_stored_representative`), so the reader's
consistency check still applies.  Each stored wavefunction is read at most once
even when a path revisits it many times.  A k-point that no stored k-point and
operation can reach is reported rather than silently mismatched.

### 6.4 Spin- and polarization-resolved weights

`weights_from_coefficients(..., component_resolved=True)` and
`compute_plane_wave_unfolding_weights(..., component_resolved=True)` return the
weight split over the spinor/polarization components.  Summing over the
component axis reproduces the ordinary weight exactly, so the sum rule is
untouched.

### 6.5 Two reader bugs in the VASP WAVECAR path

* **G-vector ordering.**  `generate_vasp_g_vectors` produced an
  energy-sorted list.  WAVECAR stores coefficients in VASP's FFT scan order —
  third axis outermost, first axis innermost, each axis running over the wrapped
  index sequence `0, 1, ..., M, -M, ..., -1`.  Any other order pairs every
  coefficient with the wrong G-vector and produces meaningless weights without
  any warning.  The generator was rewritten to reproduce that order, and it now
  raises instead of silently truncating when the generated count does not match
  the file.
* **Spinor detection.**  Record tag 53300 was being treated as a noncollinear
  spinor file.  It is not: it is the Γ-only reduced storage.  VASP writes spinor
  wavefunctions with the *ordinary* complex tags, and what marks them is that the
  k-point record reports `2 * n_g` coefficients per band.  Detection is now based
  on that count, and `WavecarHeader.gamma_only` replaces the incorrect
  `spinor_components` field.

### 6.6 The moiré cell of a layered stack

`build_moire_reciprocal_lattice` returns `B_a - B_b`, which cannot be inverted
to obtain the real-space moiré cell: two layers of a stack share their stacking
vector, so that difference has a zero row and is singular *for every layered
system* (`UnfoldLab.moire_reciprocal_singular_of_shared_axis`).  The new
`TwistedUnfoldingProblem.moire_lattice` therefore inverts only the block
transverse to the stacking axis and takes the stacking vector from the
supercell, rejecting reference pairs that share no stacking direction or have
equal in-plane reciprocal lattices.

### 6.7 High-level workflows are no longer placeholders

`UnfoldingProblem.unfold`, `TwistedUnfoldingProblem.unfold_to_reference`, and
`TwistedUnfoldingProblem.unfold_to_moire_bz` used to raise
`NotImplementedError`.  They now run the plane-wave kernel through a single
shared entry point, `unfold_wavecar_to_lattice`, which needs nothing but the
integer transform `A_sc = T A_target` — so the target may be a primitive cell, a
reference layer of a twisted stack, or a moiré cell.  The band-path abscissa is
accumulated in Cartesian reciprocal space (`cartesian_path_distances`), because
equal fractional norms can correspond to different physical distances
(`UnfoldLab.exists_equal_fractional_distinct_cartesian`).  Projection selectors
are still parsed but not applied, and passing one is rejected explicitly.

### 6.8 Remaining caveats

* The PAW/USPP normalization caveat of §4.1 stands: weights are those of the
  pseudo wavefunction.
* The QE `alat` caveat of §4.2 stands.
* Symmetry-reduced unfolding (§6.3) was wired up for the VASP backend only; the
  QE path raised a clear error rather than ignoring the request.  *(Superseded
  in the fourth pass: §8.2 threads the operations through the QE `.save`
  workflow as well, so the restriction now only applies to the QE
  coefficient-table input, which carries no k-point labels to symmetrize.)*
* The user supplies the point-group operations; the library does not detect the
  space group of the supercell.  Operations that are not symmetries of the
  supercell are rejected (`T S_pc T^-1` must be integral), but the library
  cannot check that they are symmetries of the *Hamiltonian*.  *(Superseded in
  the fifth pass: §9 detects the space group of the structure, so the
  operations no longer have to be supplied.  The last sentence still stands —
  symmetry of the structure is not symmetry of the Hamiltonian, for instance
  under an applied field or a magnetic order the geometry does not show.)*

## 7. Third pass: projected unfolding

### 7.1 Projection selectors were parsed but never applied

`UnfoldingProblem.unfold(projections=...)` raised `NotImplementedError`: the
selector grammar of `docs/projections.md` existed, but nothing resolved a
selector against a structure and nothing combined it with the unfolded weights.

Three pieces were added.

* **A `PROCAR` reader** (`unfoldlab.io.procar.read_procar`).  It handles the
  collinear, spin-polarized and noncollinear layouts (one or four ion tables per
  band, one block per spin channel) and skips the `LORBIT = 12` phase tables,
  which are recognized by their doubled row width.  The noncollinear
  magnetization tables are kept separately from the charge table rather than
  being averaged into it.  Missing `(k-point, band)` entries are an error, not a
  silently zero-filled row.
* **Selector resolution** (`unfoldlab.core.site_projection`).  Selectors of the
  same namespace are combined with OR, different namespaces with AND.
  `species`, `atom`, `orbital`, `layer` and `surface` are resolved from geometry;
  `sublattice`, `region`, `interface`, `valley`, `defect_shell` and the role tags
  are user conventions and are resolved from an explicit `site_groups` mapping,
  raising a clear error when it is missing rather than guessing.
  `distance_from_defect` uses the certified minimum-image distance of §6.1, so
  a defect shell is correct for a non-orthogonal cell.
  Layer detection projects onto the normal of the plane spanned by the two
  transverse lattice vectors — using the fractional coordinate along the
  stacking axis instead would split or merge layers whenever the stacking vector
  is sheared — and cuts the layers at gaps larger than a tolerance, starting
  from the largest gap (the vacuum of a slab).
* **The combination rule** (`unfoldlab.workflows.projected`), together with its
  formal model `lean-proofs/RequestProject/Unfolding/Projection.lean`.

### 7.2 What the projected weight is, and is not

The projected weight is `w_P(k; K, n) = f_P(K, n) * w(k; K, n)`.  This is the
projector-assisted approximation: the character table is resolved in the
supercell k-point `K` and the band index, but not in the primitive k-point, so
every member of the fiber over `K` receives the same fraction.  It is not a
`k`-resolved projected spectral function, and the docstrings say so.

What it does satisfy exactly is proved:

* `UnfoldLab.projectedWeight_le` — a projection never creates spectral weight;
* `UnfoldLab.sum_projectedWeight_of_partition` — the projected weights of a
  partition of the character table sum back to the plain weight, so a projection
  only redistributes it;
* `UnfoldLab.sum_fiber_projected_partition` — the fiber sum rule survives:
  summing over the fiber and over a full partition returns one;
* `UnfoldLab.IsFiberRepr.sum_projectedWeight` — for a *single* group the fiber
  sum is that group's fraction.  A projected run must therefore not be checked
  against a sum rule of one, which is the mistake `max_band_sum` invited in §2.3.

### 7.3 Two normalization traps

VASP's sphere projections do not sum to the norm of the band: charge in the
interstitial region is not in any sphere.  Two ways of dealing with that are
wrong and are ruled out by counterexample.

* Dividing by a partial total — for instance a `tot` column that omits part of
  the table — breaks the partition identity
  (`UnfoldLab.exists_partial_normalization_sum_ne_one`).  `projection_fractions`
  therefore always divides by the sum over the whole `(site, orbital)` table.
* Feeding a signed table (a noncollinear magnetization column) to the same
  formula can produce a "fraction" above one
  (`UnfoldLab.exists_signed_table_fraction_gt_one`), so negative entries are
  rejected outright.

A band whose total projected character is numerically zero gets a fraction of
zero, which keeps `w_P ≤ w` in that degenerate case too.

## 8. Fourth pass: provenance, reproducibility and backend parity

### 8.1 An unfolded table could not be traced back to its inputs

The output of a run is a plain text table of `(distance, energy, weight)`.  The
numbers in it mean nothing without the transformation matrix, the spin channel,
the energy zero, the weight mode and the identity of the input files: the same
table is produced by a `2×2×1` and a `4×1×1` supercell run, and a WAVECAR that
was overwritten by a later calculation leaves no trace.

`unfoldlab/io/serialization.py` adds a *run manifest*: the backend, the weight
mode, the transformation, the reference energy, the spin channel, the projection
selectors, the package version, a UTC timestamp, and for every input file its
path, its size and its SHA-256 digest (hashed in 1 MiB chunks so a multi-gigabyte
WAVECAR is never read into memory at once).  `unfold --manifest` writes it, and
`unfold --json` writes the effective band structure itself as JSON with the
manifest embedded.  Both documents carry a `schema` tag and a `schema_version`;
`read_ebs_json` refuses a foreign document and refuses a version it is too old
to understand, rather than silently mis-reading it.  `--no-hash-sources` skips
the digests when the inputs are too large for that to be worth it.

### 8.2 QE could not use the symmetry-reduced path

The plumbing for symmetry-reduced unfolding stopped at the VASP workflow: the
`operations` and `lattice_alat` arguments were accepted by the QE weight
routines but never forwarded, and the backend dispatcher rejected the
combination outright.  They now thread through `compute_qe_weights`,
`build_qe_effective_band_structure`, `unfold_qe_bands`, `compute_backend_weights`
and `unfold_backend_bands`, and the CLI exposes `--lattice-alat` on both
`weights` and `unfold`.  Only the coefficient-table input is still rejected with
`--symmetry`, and for a substantive reason: a bare table of coefficients carries
no k-point labels, so there is nothing to map an operation onto.  This
supersedes the third bullet of §6.8.

## 9. Fifth pass: the symmetry operations are now derived, not assumed

### 9.1 The user had to supply the point group by hand

Symmetry-reduced unfolding needs the point-group operations of the cell, and
§6.8 recorded that the library simply took them from the user.  That is both a
usability gap and a correctness hazard: an operation that is not a symmetry of
the structure produces silently wrong weights for every k-point it is used on.

`unfoldlab/core/spacegroup.py` derives them.  In the fractional column
convention an integer matrix `M` maps the lattice onto itself and preserves all
distances exactly when it preserves the metric tensor `G = A Aᵀ`,
`Mᵀ G M = G`, so the columns of `M` are lattice vectors with the lengths of the
basis vectors they replace.  Only finitely many integer vectors have a given
length, and the components of such a vector are bounded by Cauchy–Schwarz in
the inner product defined by `G`:

`(v_k)² ≤ (G⁻¹)_kk (vᵀ G v)`

(`UnfoldLab.sq_component_le_of_quadForm`).  `lattice_point_group` enumerates
exactly that box, so it is *complete*: the search cannot miss an operation
(`UnfoldLab.sq_entry_le_of_metricPreserving`).  `space_group_operations` then
filters the lattice symmetries by an explicit site-permutation check, trying the
translations that carry one reference site of the rarest species onto a site of
the same species; non-symmorphic operations are found and flagged, and only the
rotation matters for the weights because a translation contributes a phase and
the weights depend on `|c|²`.

### 9.2 Real space and reciprocal space

The detected operations act on fractional *positions*; the unfolding weights
take operations on fractional *reciprocal* coordinates.  The conversion is
`S = (M⁻¹)ᵀ`, which is integral because a lattice symmetry is unimodular

reciprocal metric (`UnfoldLab.metricPreserving_reciprocal`).

maps to primitive coordinates with `S_pc = T⁻¹ S_sc T`, dropping the operations
for which that is not integral; what comes out is ready for `--symmetry`.  The
new `unfoldlab detect-symmetry` command exposes both modes.

The detected point-group orders are checked against the known holohedries
(48 cubic, 24 hexagonal, 16 tetragonal, 2 triclinic), against group closure, and
end to end: a k-point outside the stored wedge that `map_kpoints_to_stored`
rejects without operations is served by a detected one.

## 11. Seventh pass: inverting the fold

### 11.1 The library could fold but not unfold k-points

Every previous pass took the primitive k-path as an *input*: the user wrote
down the primitive k-points, the library folded them and looked up the matching
supercell wavefunctions.  That is fine for a band path, where the user has
chosen the path.  It is exactly wrong for the other common case: a supercell
calculation on a Monkhorst–Pack mesh, where the k-points the user has are the
*supercell* ones and the question is which primitive k-points they carry.

The theory already said how many there are — `|det T|` per supercell k-point,
`UnfoldLab.IsFiberRepr.card_eq_natAbs_det` — but the code had no way to produce
them, and §4.6 recorded the consequence: the fiber sum rule was essentially
never checkable as an equality.

The preimages are the solutions of `T k = K + m` as `m` runs over a transversal
of the finite group `ℤ³ / T·ℤ³`.  Enumerating that group is a Smith normal form
computation, so `unfoldlab.core.lattice_quotient` now provides one, in exact
Python integer arithmetic: `smith_normal_form` returns unimodular `U`, `V`, the
diagonal `D` with `U M V = D`, and the integer inverse of `U`; since `V` is
unimodular, `M ℤ³ = U^{-1} D ℤ³`, so the classes are `U^{-1} y` for `y` in the
box `∏ [0, d_i)`.  `coset_representatives` returns exactly `|det M|` of them and
refuses a singular matrix rather than looping forever.

On top of that, `unfoldlab.core.kpoints` gained

* `fiber_kpoints(K, T)` — the `|det T|` primitive k-points folding onto `K`,
  wrapped into `[0, 1)` and lexicographically sorted so runs are reproducible.
  The solve uses the exact integer adjugate rather than a general matrix
  inverse.
* `fiber_kpoint_mappings(Ks, T)` — the same expansion for a whole list, emitted
  as `KPointMapping`s with the supercell weight divided evenly, so the total
  weight is preserved.

and the CLI gained `unfoldlab fiber`, which prints the fibers and can write
them straight out as a kmap that `unfoldlab weights` and `unfoldlab unfold`
accept.  Mesh unfolding therefore no longer requires the user to work out the
preimages by hand.

### 11.2 The construction is certified, not just tested

`lean-proofs/RequestProject/Unfolding/Coset.lean` is new.  `IsCosetRepr T ms` is the
specification the Smith-normal-form enumeration is supposed to meet, and

* `UnfoldLab.IsCosetRepr.isFiberRepr` proves that the k-points
  `k_m = (Tᵀ)⁻¹ (K + m)` built from such a list satisfy `IsFiberRepr` — they all
  fold onto `K`, they cover every k-point that does, and none is listed twice;
* `UnfoldLab.IsCosetRepr.card_eq_natAbs_det` proves that a correct list has
  exactly `|det T|` entries, which is the cheap runtime check the Python code
  performs before returning.

So the new code is not merely tested against examples: the recipe it implements
is the one the formal development proves correct, and the count it asserts is
the count the theory predicts.

### 11.3 The sum rule is now an equality that can be tested

Because a complete fiber is now constructible, the partition theorem
`UnfoldLab.IsFiberRepr.existsUnique_pwMatches` can be exercised numerically:
`tests/test_lattice_quotient.py` takes random plane-wave coefficients, sums the
unfolding weights over `fiber_kpoints(K, T)` for seven different transformation
matrices, and requires the total to be one to machine precision.  Before this
pass no test could do that, because no test could build a complete fiber.

### 11.4 A fiber k-map needed one stored wavefunction per several rows

Writing the fiber out as a k-map exposed a second gap.  Every row of a fiber
k-map names the *same* supercell k-point, but the strict reader mode demanded
one stored wavefunction per k-map row, in order, so it rejected the very file
`unfoldlab fiber` had just produced.

The capability was already there — the symmetry-reduced path with an empty
operation list matches rows to stored k-points instead of pairing them by index
— but nothing said so, and the error message did not point at it.  The `weights`
and `unfold` commands now take `--reuse-kpoints`, which selects exactly that
mode without inventing a symmetry file, and the count-mismatch error names the
option.  `--reuse-kpoints` together with `--symmetry` is rejected rather than
silently ignored, because `--symmetry` already implies it.

`tests/test_fiber_workflow.py` runs the whole loop on a synthetic WAVECAR:
`fiber` writes the k-map, the unfolding consumes it, the two rows of the fiber
carry weights that add to one for every band, and `diagnose_fiber_sum_rule`
reports one complete fiber with no violation.  The strict mode is tested too —
it must still refuse the file when the flag is absent.

## 12. Eighth pass: unfolding without plane waves

### 12.1 Every backend assumed a plane-wave basis

The whole package — the QE readers, the VASP `WAVECAR` reader, the coefficient
tables, the matching kernel, the sum-rule diagnostics — unfolds a state that is
given as a list of coefficients indexed by supercell reciprocal-lattice
vectors.  That is the right model for a plane-wave DFT code and the wrong one
for the other half of the field.  A tight-binding model, a Wannier
Hamiltonian, a continuum model, or any Hamiltonian matrix produces a supercell
state given by *one amplitude per (orbital, primitive cell) pair*, and there
was no way to unfold it: the roadmap listed "Wannier and tight-binding
backends" as a later milestone, and nothing in the library or in the Lean
development covered them.

This is not a matter of reformatting the input.  The plane-wave weight is the
fraction of the norm carried by the plane waves that *match* the primitive
k-point, and its sum rule is the statement that the matched sets partition the
basis (`UnfoldLab.IsFiberRepr.existsUnique_pwMatches`).  The tight-binding
weight is the squared norm of a discrete Fourier component,

`A(k, a) = Σ_R exp(-2π i ⟪k, R⟫) c(a, R)`,

and no partition of a basis is involved: the sum rule is Parseval's identity
for the finite Fourier transform of the supercell.  A partition argument cannot
prove it, and the plane-wave code cannot compute it.

### 12.2 The two finite groups are dual, and that is the whole theorem

Write `T` for the transformation matrix, in the package's row-vector
convention `A_sc = T @ A_pc`.  Two finite abelian groups of order `|det T|`
appear:

* the *cells*: the primitive cells inside the supercell are the classes of
  `ℤ³ / ℤ³ @ T` (a supercell lattice vector is `n @ T` in primitive
  fractional coordinates), and
* the *reciprocal classes* `ℤ³ / T·ℤ³` that label the members of a fiber, which
  the seventh pass already enumerated with the Smith normal form.

The pairing `⟪m, R⟫ = (T⁻¹ m) ⬝ R` is well defined modulo one in each argument
and *nondegenerate*: if `R` pairs trivially with every `m` then `T⁻ᵀ R` is
integral, i.e. `R` is a supercell lattice vector.  `UnfoldLab.sum_dualChar`
turns that into the orthogonality relation

`Σ_m exp(-2π i ⟪m, R⟫) = |det T|` if `R ∈ ℤ³ @ T`, and `0` otherwise,

from which `UnfoldLab.sum_normSq_tbAmplitude` (Parseval) and
`UnfoldLab.sum_tbWeight_eq_one` (the sum rule) follow.  The point of doing it
this way, rather than as a product of geometric series, is that it holds for a
*non-diagonal* supercell verbatim: nothing in the argument assumes that `T` is
diagonal or that the cells form a box.  `lean-proofs/RequestProject/Unfolding/TightBinding.lean`
also proves the dual orthogonality `UnfoldLab.sum_phase_pair_cells` — the
unfolding transform is unitary, not merely isometric on one side.

### 12.3 A second sum rule the plane-wave code never had

Because the transform is unitary, a *complete* set of supercell eigenstates
obeys a sum rule in the other direction as well:
`UnfoldLab.sum_tbWeight_states` proves that at a fixed primitive k-point the
weights of all `|det T| · n_orbitals` supercell states add up to
`n_orbitals`, the number of primitive bands.  That is a much sharper check than
the fiber sum rule, because it is sensitive to a wrong cell list, a truncated
band set, or a mis-ordered basis, none of which the per-state sum rule sees.
`diagnose_tight_binding_weights` reports both, and it reports the band rule as
`None` rather than as a violation when the state list is not complete, which is
the legitimate case of a band window.

The end-to-end check is the one that matters: for a supercell of a *perfect*

### 12.5 A halving bug in the Hermitian completion

The first version of `TightBindingModel.hermitized` averaged each hopping with
its conjugate partner, `t(D) → t(D)/2` and `t(-D) → t(D)†/2`.  For a user who
lists a hopping in only one direction — which is the point of the method — that
halves the physical amplitude, and it halved the on-site energy too.  It now
fills in a missing partner at full strength and takes the Hermitian part only
of a pair that is genuinely present on both sides, which leaves an
already-consistent model untouched and is idempotent.  The chain test pins the
band edges at `onsite ± 2|t|`.

### 12.7 Reading a real Wannier90 Hamiltonian

The JSON model format is convenient for toy systems, but the tight-binding
backend is only useful on real material if it can read what Wannier90 writes.
`unfoldlab/io/wannier90.py` adds `read_wannier90_hr`, which parses
`seedname_hr.dat` into the same `TightBindingModel`:

* the header gives `num_wann` and `nrpts`, followed by `nrpts` Wigner–Seitz
  degeneracies packed fifteen to a line — the reader accepts any line wrapping
  and rejects a block that overshoots;
* every hopping line is `Rx Ry Rz m n Re Im`, and the amplitude Wannier90
  stores is the physical hopping **multiplied** by the degeneracy of `R`, so the
  reader divides it back out.  Skipping that division is a classic silent error:
  it leaves the model non-Hermitian in a subtle way and misplaces bands along
  the zone-boundary directions;
* the counts are cross-checked (expected number of hopping lines, number of
  distinct lattice vectors, orbital indices inside `1..num_wann`), so a
  truncated or mismatched file fails loudly instead of unfolding nonsense;
* `hermitize=True` is offered because a disentangled calculation can leave a
  small asymmetry, but it is off by default: an hr file already contains both
  `R` and `-R`, and silently symmetrizing would hide a genuinely broken file.

`unfoldlab model unfold` grew `--format auto|json|hr` (auto picks by extension)
and a repeatable `--onsite cell,orbital,value`, so a defect can be placed in a
Wannier supercell straight from the command line without editing a file.
`tests/test_wannier90.py` covers the degeneracy division, complex multi-orbital
blocks, the malformed-file errors, and an end-to-end check that a chain read
from hr data unfolds to `onsite + 2t·cos(2πk)`.

### 12.8 The supercell Hamiltonian was quadratic in the number of cells

The first assembly of the supercell Bloch Hamiltonian looped over *all pairs* of
primitive cells and, for each pair, tested every hopping for membership of the
supercell lattice — `O(n_cells² · n_hoppings)` work, repeated for every k-point.
That is wasted effort: for a fixed hopping `D` and a fixed cell `R` there is
*exactly one* cell `R'` with `R' ≡ R + D` modulo the supercell lattice, so the
supercell Hamiltonian has only `n_hoppings · n_cells` non-zero blocks.

Finding that one column cheaply needs a canonical label of a class of
`Z³ / Z³ @ T`, and the adjugate criterion already provides one: `v ↦ v @ adj(T)
mod |det T|` is a homomorphism whose kernel is exactly the supercell lattice, so
it separates the classes exactly and can be hashed.  The couplings and the
translations `L = R + D - R'` that carry the k-dependence are the same for every
k-point, so they are now built once per `(model, transform)` and reused across
the whole k-point list.  A 72-cell supercell of a three-orbital model builds
about a hundred times faster, and `TightBindingModel` gained a batched
`bloch_hamiltonians` so that a band path is one contraction plus one batched
`eigvalsh` instead of a Python loop.

The optimization is pinned by a test that compares it against the definition
written out as a triple loop, for all seven transformation matrices in the
suite, and the perturbation indices are now range-checked rather than silently
wrapping around the matrix.

### 12.9 Unfolding along a primitive band path

`unfold_tight_binding_model` answers "what does this supercell k-point unfold
to?", but what a user plots is the opposite question: "how much weight does this
*primitive* k-point carry?".  `unfold_tight_binding_path` answers that one — for
each requested primitive k-point the supercell Hamiltonian is built at the
supercell k-point it folds onto, diagonalized, and every eigenstate is given its
weight at that k-point alone.  It is exposed as `unfoldlab model bands`, with
`--path 0,0,0:0.5,0,0:0.5,0.5,0` and `--points`, and writes the usual effective
band structure JSON with path abscissae.

This is also where the exactness claim finally became a theorem rather than a
numerical observation.  `UnfoldLab.tbWeight_blochState` states that a supercell
state that *is* a primitive Bloch state — `UnfoldLab.blochState`, the state a
perfect crystal produces — unfolds to weight exactly one at the fiber member it
came from and exactly zero at every other member.  Band folding is undone
exactly, for a non-diagonal supercell as much as for a diagonal one; a defect or
a distortion is then measured by how far the weights depart from that delta.

### 12.10 Which Wannier gauge convention does the unfolding assume?

None, and that is now a theorem.  Wannier90 output can be written with the
orbital positions inside the cell absorbed into the Bloch phase or not
(the "lattice" and "atomic" conventions), and the two differ by a phase
`e^{-2πi k·τ_a}` on every amplitude of orbital `a`.  That phase is constant
along the sum over cells, so it factors out of the Fourier amplitude and
disappears from the modulus: `UnfoldLab.tbWeight_orbital_phase` states that
multiplying the amplitudes of each orbital by any unit-modulus phase leaves
every weight unchanged.  A user therefore cannot get the weights wrong by
choosing the wrong convention, which is worth knowing, because the *band
energies* very much do depend on it.

## 13. Tenth pass: spin texture and adaptive broadening

### 13.1 Component-resolved weights are not a spin texture

The noncollinear path already split a weight into `Σ|c_up|²` and `Σ|c_down|²`
over the matching plane waves, and it is tempting to call the difference "the
spin".  It is only the *longitudinal* part.  A spinor state is described by the
full Bloch vector

```text
S = (2 Re(conj(c_up) c_down), 2 Im(conj(c_up) c_down), |c_up|² - |c_down|²),
```

and the two transverse components are exactly the information that squaring the
components separately throws away.  For a state polarized along `+y` the
component-resolved weights are equal and their difference vanishes, so a
spin-orbit-split band with in-plane spin — the interesting case, and the reason
one runs a noncollinear calculation at all — would be reported as unpolarized.

`unfoldlab.core.plane_waves.spin_texture_from_coefficients` computes the full
vector, restricted to the matching plane waves and normalized by the norm of the
state, and `spin_expectation_from_coefficients` gives the same quantity for the
whole state.

Two facts make the result safe to plot, and both are proved in
`lean-proofs/RequestProject/Unfolding/Spin.lean` rather than assumed:

* **the texture is bounded by the weight**, `‖S(k)‖ ≤ w(k) ≤ 1`
  (`UnfoldLab.norm_spinTexture_le_pairWeight`).  The proof is worth stating
  because it is the reason the bound is *tight*: a single two-component spinor
  is a pure state, so the length of its Bloch vector equals its norm exactly,
  and the triangle inequality over the matching plane waves gives the bound with
  equality precisely when they all point the same way.  A texture longer than
  its weight is therefore not a rounding artefact but a sign that the two tables
  came from different states, which is what `diagnose_spin_textures` reports as
  `max_texture_excess` and what the backend warns about;
* **the spin sum rule**, `UnfoldLab.IsFiberRepr.sum_spinTexture`: the textures
  of the `|det T|` primitive k-points of a fiber add up to the spin expectation
  value of the supercell state.  This is the vector analogue of the weight sum
  rule, and unlike it, it also constrains the transverse components.

`UnfoldLab.spinPartial_apply_two` pins the `z` component to the difference of
the component-resolved weights, so the two code paths cannot drift apart.

### 13.2 A spin texture must not be reconstructed from an irreducible wedge

Unfolding from a symmetry-reduced wavefunction set works because the weight is
invariant under a point-group operation, `w(S k; S K) = w(k; K)`
(`UnfoldLab.weight_symmetry`).  The spin is *not* invariant: it is a
pseudovector, so at `S k` the texture is the stored texture **rotated** by `S`,
and for a spinor wavefunction that rotation is fixed only up to the choice of
SU(2) lift and is reversed by time reversal.  Reusing a stored texture unrotated
would silently point the spin the wrong way — a plausible-looking plot with the
spin arrows wrong on every symmetry image.

`compute_spin_texture_from_wavecar` therefore has no symmetry-reduced mode, and
both the workflow dispatcher and the CLI refuse `--spin-texture` together with
`--symmetry` or `--reuse-kpoints`, with that reason in the message.  The weights
themselves remain available in symmetry-reduced mode as before.

### 13.3 Broadening was fixed-width, which is wrong for a steep band

A single Gaussian width for the whole band structure is a compromise: wide
enough to make a steep band look continuous between neighbouring k-points, and
therefore too wide to resolve a flat one.  `EffectiveBandStructure.adaptive_widths`
returns a per-state width `scale · |dE_n/ds| · ds` — the energy a band sweeps
over the local spacing of the path abscissa — clipped from below by a positive
floor (a zero width is not a kernel) and optionally from above.
`spectral_function` now accepts either a scalar or a table broadcastable to
`(n_kpoints, n_bands)`.

The property that makes this legitimate is that the total weight is still
conserved: every state is broadened with its *own* normalized kernel, so the
integral over energy is unchanged.  That is `UnfoldLab.integral_adaptiveSpectralFunction`,
proved alongside the fixed-width version, with `adaptiveSpectralFunction_const`
recording that a fixed width is the special case.  Without it, a
velocity-dependent width would be indistinguishable from a reweighting of the
bands, which would corrupt exactly the quantity the unfolding computes.

## 14. Eleventh pass — fat bands for tight-binding models, and `seedname_tb.dat`

### 14.1 A Wannier supercell could be unfolded, but not decomposed

Every plane-wave backend can already answer "which *species*, *site*, *layer* or
*orbital* carries this unfolded weight" through `core/site_projection.py`.  The
tight-binding backend could not: `tight_binding_weights` returns one number per
`(k-point, state)` and nothing said how that number is distributed over the
orbitals of the primitive cell.  For a Wannier model of a heterostructure or a
defect supercell that is precisely the interesting question — the unfolded band
is only useful once you know which layer or sublattice it belongs to.

The definition added is the obvious one, and the reason to write it down
carefully is the normalization.  The projected weight of a group `S` is

```
W_S(k) = (sum_{a in S} |A(k, a)|^2) / (|det T| * sum_{a, R} |c(a, R)|^2),
```

with the *full* state norm in the denominator.  Renormalizing each group by its
own norm instead — the tempting alternative — would make every group's weights
sum to one over the fiber and destroy the additivity that makes a fat-band plot
readable.  With the full norm the three properties one actually wants are true
and are proved in `TightBinding.lean`:

* `tbOrbitalWeight_union_of_disjoint` — disjoint groups add, so a partition of
  the orbitals reproduces `tbWeight` exactly;
* `tbOrbitalWeight_le_tbWeight` (with `tbOrbitalWeight_mono`) — a group never
  claims more than the total;
* `sum_tbOrbitalWeight_eq_norm_share` — over a complete fiber the group's
  weights add up to the group's *share of the state norm*, which specializes to
  the old sum rule `= 1` for the full orbital set.

The last one is the sharpest statement: it says the fiber sum of a fat band is a
property of the state alone and does not depend on the k-point, which is what
makes it safe to read the fat band as "how much of this state is layer 1".

`tight_binding_orbital_weights` and `unfold_tight_binding_path_projected`
implement this, and `unfoldlab model bands --group 0,1 --group 2,3` exposes it;
the group shares are printed and the full `(n_groups, n_kpoints, n_states)`
table is stored in the run's metadata.  `tests/test_tight_binding_projection.py`
checks each of the three properties numerically.

### 14.2 `seedname_hr.dat` is not enough to describe a Wannier model

The Wannier90 reader only handled `seedname_hr.dat`, which carries hoppings and
nothing else: no lattice, so no Cartesian band-path abscissa without a second
file, and no position operator, so no Wannier centres and therefore no way to
build the orbital groups that section 14.1 just made useful.

`read_wannier90_tb` reads `seedname_tb.dat`, which carries all three.  Points
worth recording:

* The Hamiltonian blocks are divided by the Wigner-Seitz degeneracy, exactly as
  in the `hr` reader, and so are the position blocks; `divide_by_degeneracy=False`
  is available for a file that was written with the division already applied.
* The centres are the diagonal of the `R = 0` position block.  They are
  *metadata*: `UnfoldLab.tbWeight_orbital_phase` proves that moving a Wannier
  function inside its cell — which is what changing the position convention
  does — leaves every unfolding weight unchanged.  So the position operator can
  never change an answer; it can only label one.  `Wannier90TB.centre_structure`
  turns the centres into a `Structure` so that `detect_layers` can produce the
  groups directly.
* The position operator is optional: a file that stops after the Hamiltonian
  blocks is accepted with `positions = None` rather than rejected.

## 15. Twelfth pass — reading big files in blocks, and closed-form benchmarks

### 15.1 A `WAVECAR` had to fit in memory

Every reader loaded a whole k-point — all bands, both spinor components — before
any weight was computed.  For a production noncollinear supercell that is
several gigabytes for a single k-point, and the weights themselves are tiny: the
data is streamed through a reduction and then thrown away.  Nothing about the
mathematics required it to be resident all at once.

The readers now take a band block.  `WavecarReader.read_kpoint_wavefunction`
and `plane_wave_kpoint_data` accept `band_start` / `band_count`, the QE readers
grew a `band_block()` helper (`read_wfc_hdf5` slices the `evc` dataset,
`read_wfc_dat` walks past the skipped records without materializing them), and
`compute_weights_from_wavecar(..., band_chunk=m)`,
`compute_weights_from_qe_save(..., band_chunk=m)` and the CLI's `--band-chunk`
drive the loop.  `compute_plane_wave_unfolding_weights_chunked` is the
accumulator: an outer iterable of k-points, an inner iterable of consecutive
band blocks, with runtime checks that the blocks of one k-point really do share
a k-point and a G-list.

Two things were worth proving rather than assuming, and are in `Chunking.lean`:

* `weight_biUnion` — chunking over *plane waves* is exact.  This is not quite
  trivial because the weight is a ratio: one has to accumulate the matched and
  the total norm separately and divide only at the end, and the `0/0 ↦ 0`
  convention has to survive the split.
* `bandWeights_flatten` — chunking over *bands* is exact, and
  `bandWeights_flatten_length` says the concatenated table has the length one
  expects.  The spin analogues (`spinPartial_biUnion`, `pairPartial_biUnion`,
  `pairNorm_biUnion`) cover the noncollinear cross terms.

One honest caveat, encoded in the tests rather than hidden: the chunked and the
unchunked path agree to about `1e-12`, not bit for bit, because summing in
blocks reassociates the floating-point additions.  `tests/test_band_chunking.py`
asserts that tolerance, and separately asserts that only one block is resident
at a time — otherwise a "chunked" path that quietly reads everything would pass.

### 15.2 A malformed k-map raised `IndexError`

`read_kmap` indexed the split row directly, so a short or comma-separated line
produced a bare `IndexError` with no file name, no line number and no hint about
the expected format.  It now reports the file and the line, accepts
whitespace-separated as well as tab-separated files, and `KMAP_COLUMNS` records
the expected layout (`ik`, `s_pc`, `k_pc(3)`, `K_unfolded(3)`, `K_folded(3)`,
optional label).

### 15.3 An effective band structure could only be written as JSON

`EffectiveBandStructure` holds four float arrays whose size is
`n_kpoints × n_energies`; as JSON that is both large and lossy in the last
digits.  `write_ebs_hdf5` / `read_ebs_hdf5` store them as native `float64`
datasets with the run manifest in the attributes, `EBS_SCHEMA` versions the
layout, and `write_ebs` / `read_ebs` dispatch on the suffix — so
`unfoldlab unfold --json run.h5` now writes HDF5 with no other change.

### 15.4 Nothing checked the code against a case with a known answer

The suite tested internal consistency — sum rules, invariances, backend parity —
but almost nothing pinned a number to an independently known value.
`docs/benchmarks.md` and `tests/test_benchmarks.py` add five closed-form cases:
the perfect chain supercell for `N = 2..5` (the unfolded band must be the
primitive cosine band), the anisotropic square lattice (a non-cubic supercell,
so the fold is genuinely two-dimensional), the dimerized (SSH) chain whose gap
is exactly `2|t₁ − t₂|`, a single plane-wave state (weight exactly one at one
fiber member), and a defect chain where only the sum rule survives.

The instructive failure while writing them: the first version asserted that
exactly one supercell state carries the weight at each primitive k-point.  That
is false whenever the fiber member is degenerate — any unitary mixing inside the
degenerate subspace redistributes the weight between the eigenvectors, and the
individual numbers are then an artefact of the diagonalizer.  Only the *total*
weight and the *energies* carrying it are basis independent, and that is what
`_assert_single_primitive_band` now checks.  `Ideal.lean` proves the clean case:
if every plane wave of a supercell state belongs to one primitive k-point, the
weight there is exactly one and exactly zero at every other fiber member
(`IsFiberRepr.weight_ideal`).

### 15.5 A matrix-valued on-site perturbation crashed opaquely

was a matrix and failed later inside NumPy with a shape `TypeError`.  It now
rejects it up front with a message saying a single on-site energy shift is

## 16. Fourteenth pass — degenerate multiplets, and the missing half of the mesh

Two gaps of the same kind: a number the code reported as if it were physical
but which depends on a convention, and a reduction of the k-point mesh that
every plane-wave code performs but that the operation detector could not
express.

### 16.1 The weight of a band inside a degenerate multiplet is not physical

`docs/benchmarks.md` and §15.4 already noted the symptom: when a fiber member is
degenerate, the split of the weight between the individual eigenvectors is an
artefact of the diagonalizer, because any unitary mixing inside the degenerate
subspace redistributes it.  The tests were written around the problem, but
nothing in the library said so to a user, and nothing produced the
basis-independent number instead.

`lean-proofs/RequestProject/Unfolding/Degeneracy.lean` proves what is invariant.  A
multiplet is a family `c : Fin m → ι → ℂ` of coefficient vectors, a gauge change
is `mixStates U c` for a unitary `U`, and

* `sum_normSq_mulVec_of_unitary` — a unitary matrix preserves the total
  intensity the multiplet puts on each individual plane wave;
* `subspacePartialNorm_mix`, `subspaceTotalNorm_mix`, `subspaceWeight_mix` —
  hence the matched norm, the total norm and the weight of the multiplet are all
  unchanged by the gauge;
* `IsFiberRepr.sum_subspaceWeight_eq_one` — the multiplet weight still obeys the
  fiber sum rule, so nothing is lost by reporting it instead of the members;
* `subspaceWeight_eq_average_of_normalized` — for normalized states it is the
  plain average of the member weights.

`unfoldlab/core/degeneracy.py` implements the numerical side:
`group_degenerate_bands` partitions the bands of a k-point by energy (single
linkage at `tol`, so the grouping does not depend on the order the bands arrive
in), `degeneracy_averaged_weights` replaces the weights of a multiplet by their
average — which preserves the group total exactly, hence every sum rule — and
`subspace_weights` collapses the band axis to `(energy, multiplicity, weight)`
triples.  `degeneracy_report` quantifies the damage: `max_spread` is the largest
deviation of a per-band weight from its multiplet average, i.e. how much a
reported per-band weight could change under a different diagonalizer, and
`max_group_width` exposes single-linkage chaining, which is the one failure mode
of the grouping rule.  `unfoldlab degeneracy --input run.json` prints the
multiplet table and, with `--out`, writes the gauge-invariant copy.

`tests/test_degeneracy.py` includes the experiment that makes the point: an
orthonormalized three-state multiplet is mixed by a random unitary matrix, and
the individual unfolded weights move while their sum does not.

### 16.2 A non-centrosymmetric crystal could not use its own reduced mesh

Symmetry-reduced unfolding (§ on the tenth pass, `core/symmetry.py`) takes the
point-group operations of the supercell.  But a plane-wave code reduces its
k-point mesh by time reversal as well: for a nonmagnetic calculation
`ψ_{-K} = conj ψ_K`, so only one of each pair `±K` is stored — and this happens
whether or not the crystal has an inversion centre.  `detect_primitive_operations`
derives its operations from the structure, so for a non-centrosymmetric crystal
it never returns `-1`, and half of the stored set was unreachable: a k-path
point folding onto `-K_f` was rejected with "the wavefunction set does not cover
this k-path" even though the data were there.

`lean-proofs/RequestProject/Unfolding/TimeReversal.lean` proves that the missing half needs
no reconstruction either.  `pwMatches_timeReversal` says that negating `k`, `K`
and `G` together leaves the matching condition unchanged; `weight_timeReversal`
that the conjugation of the coefficients is invisible to a weight, which sees
only `‖c‖`; and `weight_timeReversal_stored` states the recipe an implementation
can use — *to unfold `k` against the time-reversal partner of a stored file,
unfold `-k` against the file exactly as stored*.  `foldsTo_neg` confirms the
reader's `K ≡ T k` consistency check survives.  `GammaOnly.pwMatches_neg`, which
was the `K = 0` case proved separately, is now derived from the general lemma.

On the Python side `detect_primitive_operations(..., time_reversal=True)` — CLI
`unfoldlab detect-symmetry --matrix ... --time-reversal` — adjoins `-S` for
every detected operation.  Nothing else had to change: `map_kpoints_to_stored`
already implements exactly the "unfold `S_pc^-1 k` against the stored file"
recipe, and for `S_pc = -1` that is `-k`.  `tests/test_time_reversal.py` covers
the detection, the k-point mapping, the numerical identity between the
time-reversed state and the stored one, the fiber sum rule for the reversed
state, an end-to-end QE run served entirely by a time-reversal partner, and the
CLI.

The caveats are recorded with the flag: it is valid only for a time-reversal
symmetric (nonmagnetic) calculation, and it must never be used to reconstruct a
spin texture, which is odd under time reversal.  The existing refusal to produce
a texture in symmetry-reduced mode already covers the second case.

## 17. Fifteenth pass — completeness of the stored wavefunction

### 17.1 The weight does not care how the state is normalized; it does care what is missing

`weights_from_coefficients` divides the matched squared norm by the total
squared norm of the coefficients the file contains.  Two consequences had never
been stated, and the second one is a real caveat that the code was silent about.

The first is benign: because the weight is a ratio, an overall factor cancels.
`UnfoldLab.weight_smul` proves it — scaling every coefficient by any nonzero
complex number leaves the weight unchanged — so a file written with a different
normalization convention, or with an arbitrary phase per state, unfolds
correctly.  Only the ray of the state matters.

The second is not benign.  The denominator is the norm of *what the file holds*,
not of the physical state.  For a PAW or ultrasoft calculation the plane-wave
coefficients are the pseudo wavefunction; the augmentation charge inside the
spheres is not in the file and cannot be unfolded from it.  The same arithmetic
applies to any other missing part — a reader that drops components, a truncated
file, a cutoff applied after the fact.  In all of these the weights are computed
from a subset of the expansion, and the honest question is how wrong they can
be.

`UnfoldLab.weight_truncation_bound` answers it: if the complete state is
normalized and a fraction `δ` of its squared norm is missing, then every weight
computed from the remainder is within `δ / (1 - δ)` of the true one.  The proof
is elementary — the matched norm and the total norm both lose at most the
missing part — but it turns an unquantified caveat into a number, and it is
sharp in the sense that nothing better can be said without the missing
components.  A companion statement, `UnfoldLab.weight_perturbation_bound`, does
the same for a *perturbed* rather than truncated state: two normalized
coefficient vectors at `ℓ²` distance `ε` give weights within `2 ε` of each other,
which is the bound to use when comparing two codes or two convergence settings.

### 17.2 What the code now reports

* `unfoldlab.core.plane_waves.state_norms_from_coefficients` returns the stored
  squared norm of every band of a k-point.
* `unfoldlab.core.unfolding.diagnose_state_norms` summarizes a whole
  `(n_kpoints, n_bands)` table as a `StateNormDiagnostics`: the smallest,
  largest and mean stored norm, the number of states with no plane-wave content
  at all, the largest missing fraction, and — through
  `truncation_weight_error_bound`, which is exactly `δ / (1 - δ)` — the worst
  case error this implies for any weight in the run.
* `unfoldlab.io.vasp_wfc.state_norms_from_wavecar` and
  `unfoldlab.io.qe_wfc.state_norms_from_qe_save` produce that table from a
  `WAVECAR` or a `.save` directory, honouring `band_chunk` so the check costs no
  more memory than the unfolding itself.  A gamma-only file is expanded to the
  full `{G, -G}` basis first, so the number reported is the norm of the physical
  state and not of the stored half.
* `unfoldlab norms --wavecar ... | --qe-save-dir ... --nbnd N` prints the
  summary and, with `--report`, writes the full table as JSON.

The empty-state count is worth its own line in the report: a state whose
coefficients are all zero is given a weight of zero by convention rather than a
division by zero, so in the weight table it is indistinguishable from a state
that genuinely has no primitive-cell character.

`tests/test_state_norms.py` covers the readers, the diagnostics and the CLI, and
checks both proved bounds numerically on random states — including that the
truncation bound is not vacuous, i.e. that some draw comes within a factor of
twenty of it.

### 18.2 A mass defect is not an on-site term

`unfoldlab.core.phonons` unfolds phonons by handing the mass-weighted force
constants to the tight-binding kernel, which is exactly right, and the only
supercell defect it could express was `perturbations`: an additive term on the
diagonal of the mass-weighted matrix.  That covers a stiffened bond or a frozen
distortion.  It does *not* cover an isotope, a substituted atom, or a
mass-disordered alloy — and those are among the most common reasons to build a
phonon supercell in the first place.

The mathematics is short enough to state here.  With site-dependent masses the
dynamical matrix is

```text
D_ab = Phi_ab / sqrt(m'_a m'_b) = S_a D^ref_ab S_b,   S_a = sqrt(m_a / m'_a)
```

so changing one mass rescales a whole *row and column*, not one diagonal entry.
`UnfoldLab.dynMatrix_massScale` is that identity and
`UnfoldLab.mass_change_not_diagonal_shift` is its consequence: as soon as the
substituted site is coupled to anything, no diagonal term added to the original
matrix reproduces the new one.  A user who modelled an isotope as an on-site
term was not making an approximation, they were computing a different system.

The new `lean-proofs/RequestProject/Unfolding/Phonons.lean` also settles the two questions
that come with it:

* `dynMatrix_mulVec_iff` — diagonalizing `D` is the same as solving the
  generalized problem `Phi u = omega^2 M u`, with `u = M^{-1/2} e`;
* `massDisplacement_inner` and `massDisplacement_not_normalized` — displacement
  patterns are orthonormal only in the mass-weighted inner product, so the
  object that must be fed to the unfolding weights is the eigenvector `e`.  The
  code already did this, and now there is a reason on record rather than a
  coincidence.
* `acoustic_zero_mode` — if the force constants obey the acoustic sum rule, a
  rigid translation is an exact zero mode of the dynamical matrix *whatever the
  masses are*.  So a mass defect can never by itself lift the acoustic branches
  off zero at Gamma, and `acoustic_sum_rule_deviation` remains the right
  diagnostic when they do come off.

* `unfoldlab.core.tight_binding` gained `site_scaling`, a `(n_cells,

* `unfoldlab.core.phonons` gained `supercell_site_masses` (the `(|det T|,
  n_atoms)` mass table, from `(cell, atom, mass)` substitutions),
  `mass_site_scaling` (the `sqrt(m / m')` factors) and
  `supercell_dynamical_matrix`, and `unfold_phonon_path` /

## 19. Seventeenth pass — the type annotations, and the two bugs behind them

The package annotates every public function, but nothing checked the
annotations, so they had drifted into decoration.  `mypy unfoldlab` reported 71
errors across 19 of the 46 source files.  This pass took that to zero and made
`mypy unfoldlab` the fourth gate, alongside `pytest`, `ruff` and `lake build`.

Most of the 71 were noise of a familiar kind — `np.linalg.inv` returning
`floating[Any]` where the signature promised `float64` — but two were real.

### 19.1 `datetime.UTC` on Python 3.10

`io/serialization.py` stamped every run manifest with
`datetime.now(UTC)`, importing `UTC` from `datetime`.  That name was added in
Python **3.11**; `pyproject.toml` advertises `requires-python = ">=3.10"`.  On a
3.10 interpreter the import fails and *the whole package fails to import*, since
`serialization` is reached from `unfoldlab.cli.main`.  Nothing caught it because
the development environment is 3.11.  The fix is `timezone.utc`, which is
identical and available everywhere; `mypy` with `python_version = "3.10"` now
guards the whole package against the same class of mistake.

### 19.2 A fall-through in `unfoldlab norms`

The command takes exactly one of `--wavecar` and `--qe-save-dir`, and enforced
it with

```python
if (wavecar is None) == (qe_save_dir is None):
    raise typer.BadParameter(...)
```

which is correct, but the code below then branched `if wavecar is not None: ...
else: ...` — so the type checker (and a future reader) had no way to know the
`else` branch had a directory.  Worse, the guard and the branch were far apart:
any later edit that relaxed the guard would silently pass `None` into
`state_norms_from_qe_save`.  The branch is now `if wavecar / elif qe_save_dir /
else raise`, which needs no invariant held at a distance.

### 19.3 The three type aliases

Three genuinely loose interfaces were widened rather than papered over:

* `TransformLike = NDArray[int64] | NDArray[float64]` (`core/numerics.py`).  The
  transform argument of the readers, the plane-wave kernel and the workflows was
  declared `float64`, but callers pass `TransformationMatrix.matrix`, which is
  `int64` by construction, and every consumer rounds anyway.  Twenty-odd
  signatures now say what they accept.
* `OrbitalGroups = Sequence[Sequence[int] | NDArray[int64]]`
  (`core/tight_binding.py`).  `_validate_orbital_groups` normalizes groups to
  index *arrays* and its own output was then not acceptable to the function it
  feeds.
* `BroadeningKind` and `BackendCode` already existed as `Literal` aliases in
  `core/spectral.py` and `workflows/backend.py`, but the CLI parsed both into a
  bare `str`.  `_parse_code` and the new `_parse_broadening_kind` now return the
  literal type, so a typo in a `Literal` member is a type error rather than a
  runtime `ValueError` deep in a kernel.

Two more changes fall out of the same exercise.
`EffectiveBandStructure.weights` and `.distances` were declared optional but are
always filled in by `__post_init__`; the defaults are now the public helpers
`default_weights(energies)` and `default_distances(n_kpoints)`, and the fields
are non-optional, which alone removed 29 errors and one class of
`Optional`-handling boilerplate at every call site.
`TransformationMatrix.from_values(values)` is the normalizing constructor for
the callers — a parsed `--matrix` string, a detected transform — that only have
floats; the dataclass field stays exactly `NDArray[int64]`, which is what the
exact integer arithmetic downstream relies on.

## 21. Nineteenth pass — non-orthogonal (LCAO) bases

### 21.1 The Lean development arrived with four `sorry`s

The first gate of the pass caught it: `lean-proofs/RequestProject/Unfolding/Overlap.lean`
built with four `declaration uses 'sorry'` warnings, and the module was not

depended on it and nothing announced it.  The claim in `docs/progress.md` that
the formal model builds with no `sorry` was therefore false on arrival.  All
four are now proved — `ovNumer_orthonormal`, `ovWeight_orthonormal`,
`ovNumer_sub_tbNumer`, `ovWeight_smul` — the module is imported from `Main.lean`
so `lake build` covers it, and the four unused-section-variable warnings it
carried are gone (`omit [DecidableEq ι] in`, not a disabled linter).

The lesson repeats the one from pass 16: run every gate at the *start* of a
pass, and read the warnings, not only the exit status.  A file that is not
imported anywhere is invisible to a build that only checks the default target.

### 21.2 The gap the module identifies

`TightBinding.lean` and `core/tight_binding.py` unfold a supercell state with

```text
A(k, a) = sum_R exp(-2 pi i k . R) c(a, R)
W(k)    = sum_a |A(k, a)|^2 / (|det T| sum_{a,R} |c(a, R)|^2)
```

which assumes the orbitals are **orthonormal**.  Wannier functions are, and a
model tight-binding basis is by fiat.  An LCAO code — SIESTA, CP2K, OpenMX,
FHI-aims — is not: its basis functions overlap, the eigenproblem is the
generalized one `H c = E S c`, and the norm of a state is `c* S c`.  Feeding
such coefficients to the orthonormal formula is wrong in the numerator *and* in
the denominator.  There was no code path for it at all; the package would have
silently produced plausible-looking numbers.

### 21.3 What was added

`unfoldlab/core/lcao.py` implements

```text
W(k) = A(k)* S~(k) A(k) / (|det T| c* S c),
S~(k)_{ab} = sum_W exp(2 pi i k . W) S_{ab}(W)
```

with `S_{ab}(D) = <q; 0 a | q; D b>` the Bloch-twisted overlap kernel at the
supercell k-point, stored on the `|det T|` cells of the supercell and extended
to any separation by the twisted periodicity `S(D + L) = exp(-2 pi i q . L) S(D)`
(`UnfoldLab.IsBlochOverlap`).  The conventions are shared with
`supercell_bloch_hamiltonian`, so a Hamiltonian and an overlap built from the
same `q` and the same cell list are consistent by construction, and the kernel
can be read straight off a dense supercell overlap matrix
(`overlap_kernel_from_matrix`) for a code that hands one out.

The entry points are `bloch_overlap_kernel` (fold a primitive real-space
overlap table into the supercell), `validate_overlap_kernel` (Hermiticity, and
optionally positive definiteness, of the dense supercell overlap),
`lcao_norms`, `lcao_weights`, `unfold_lcao`, `solve_generalized_eigenproblem`
(Cholesky, numpy only — no new dependency) and `unfold_lcao_model`, which runs
the whole pipeline from a primitive Hamiltonian and a primitive overlap table.

### 21.4 How wrong is the orthonormal formula?

`UnfoldLab.ovNumer_sub_tbNumer` answers exactly: the numerators differ by
`sum_{ab} conj(A_a) A_b (S~_{ab} - delta_{ab})`.  The error is *first* order in
`S~ - 1`; there is no regime in which it is second order and it does not cancel
between numerator and denominator.  `diagnose_overlap_neglect` measures it on
real data.

One subtlety is worth recording, because the obvious diagnostic is empty: the
orthonormal weights of a complete fiber still add up to one for *any*
coefficients, overlap or not, because that sum rule is Parseval for the fiber
phases and knows nothing about the basis.  Neglecting the overlap therefore does
not break the sum rule — it redistributes the weight among the fiber's k-points.
The report measures that with a total variation,
`(1/2) sum_k |W_overlap - W_orthonormal|`, which is the fraction of a state's
spectral weight the orthonormal formula puts on the wrong primitive k-point.
For the same reason a *perfect* crystal in an LCAO basis unfolds correctly
either way — its eigenvector is a plane wave in the cell index — so the error
only shows up once a defect, a distortion or an alloy makes the state spread
over the fiber, which is exactly the situation unfolding exists for.

### 21.5 Benchmark

`tests/test_lcao.py` adds a closed-form case to the gallery: the non-orthogonal
chain, hopping `t`, overlap `s`, whose primitive dispersion is
`E(k) = 2 t cos(2 pi k) / (1 + 2 s cos(2 pi k))`.  A three-cell supercell of it
is diagonalized as a generalized problem and unfolded; each band lands with
weight one on a single primitive k-point and its energy reproduces the closed
form to `1e-10`.

## 22. Twentieth pass — completeness in a non-orthogonal basis

### 22.1 The gap left by pass 19

Pass 19 added the overlap-aware weight `W(k) = A(k)† S~(k) A(k) / (|det T| c† S c)`
and proved the *fiber* sum rule for it: one state spreads a total weight of one
over the `|det T|` primitive k-points of its fiber.  The complementary sum rule
— fix a primitive k-point, sum over a complete set of supercell states, get the
number of orbitals per primitive cell — was checked numerically
(`tests/test_lcao.py::test_band_sum_rule_survives_the_overlap`) but not proved,
and it is the one that is genuinely in doubt once the basis overlaps.

The reason it is in doubt: the orthonormal proof (`sum_tbWeight_states`) uses
completeness in the form `sum_s c_s c_s* = 1`.  The eigenvectors of `H c = E S c`
are orthonormal in the metric `S`, so what actually holds is
`sum_s c_s c_s* = S^-1`, a different matrix at every k-point.  Both the weight
and the completeness relation have changed, and there is no a-priori reason for
the total to come out the same.

### 22.2 The twisted convolution theorem

The new module `lean-proofs/RequestProject/Unfolding/OverlapCompleteness.lean` isolates the
reason it does.  The summand of `ovKernel`, `conj(phase(W)) S_{ab}(W)`, is a
*class function* of the cell `W`: the Bloch twist of the kernel
`S(W + L) = exp(-2 pi i q . L) S(W)` is exactly cancelled by the twist of the
phase (`ovTerm_congr`).  Summing a class function over a transversal is then
invariant under translating the argument (`sum_ovTerm_shift`, reusing
`IsCosetRepr.sum_shift`) and under reflecting it (`sum_ovTerm_reflect`, via a
new `IsCosetRepr.sum_neg`).

Those two invariances turn the product `S~(k) G~(k)` into a single sum over the
*difference* of the two cells (`ovKernel_mul_eq_convolution`), so if `G` inverts
`S` in real space — as the twisted convolution
`sum_b sum_u S_{ab}(u) G_{bc}(W - u) = delta_{ac} delta_{W,0}` — then
`S~(k) G~(k) = 1` at every k-point (`ovKernel_mul_of_inverse`).  This is the
statement that reciprocal space diagonalizes the cell convolution even when the
kernel is only *twisted*-periodic rather than periodic.

With it, the state sum of the amplitude products is `|det T|` times `G~(k)`
(`sum_states_amplitude_product`), the two overlaps cancel inside the trace, and
the across-bands total is `|os|` — the orbital count, independent of the basis
(`sum_ovWeight_states`, and `sum_ovWeight_states_of_inverse` for a caller that
has the real-space inverse rather than the reciprocal one).

The practical consequence is worth stating plainly: **the overlap-aware weights
are a genuine spectral decomposition, not merely a normalized quantity.**  Both
sum rules — over the fiber and over the bands — hold exactly, so an LCAO
unfolded band structure integrates to the right number of states, and the
runtime sum-rule checks the package already performs remain valid diagnostics
in a non-orthogonal basis rather than becoming tautologies.

## 23. Twenty-first pass — Bloch-sum conventions

### 23.1 The question

A tight-binding or LCAO supercell state arrives as a table `c[a, R]`, one
amplitude per (orbital, primitive cell).  Nothing in the table says which
Bloch-sum convention produced it, and there are three:

* **cell** — the basis is `|q; R a> = sum_L exp(2 pi i q . L) |R + L, a>`, the
  phase attached to the cell only.  This is what
  `supercell_bloch_hamiltonian` builds and what every unfolding routine in the
  package assumes.
* **atomic** — the basis carries the orbital position too,
  `exp(2 pi i q . tau_a)` on top.  Wannier90 and several LCAO codes use it.
  Relative to "cell" this is a *per-orbital* phase, constant over the cells.
* **wavefunction** — the amplitudes of the full state rather than of its
  periodic part, i.e. an extra `exp(2 pi i q . R)`.  Relative to "cell" this is
  a *per-cell* phase, constant over the orbitals.

The package had no statement about any of this, which is a gap: a user handed
eigenvectors by another code has no way to know whether the difference matters.

### 23.2 The answer, and why the two cases differ

`lean-proofs/RequestProject/Unfolding/Convention.lean` settles it.

The per-orbital phase is **a gauge**: `UnfoldLab.tbWeight_gaugeOrbital` and
`UnfoldLab.tbOrbitalWeight_gaugeOrbital` show the weight and every fat band are
*exactly* unchanged, because a diagonal factor that does not depend on the cell
comes straight out of the Fourier sum and only multiplies the amplitude by a
unimodular number.  So the atomic-versus-cell distinction, which is the one
users most often ask about, needs no action at all in an orthonormal basis.

The per-cell phase is **not** a gauge.  `UnfoldLab.tbWeight_gaugeShift` shows it
translates the entire unfolded distribution in k: the weight computed at `k` is
the true weight at `k + x`.  When the shift happens to be a difference of two
fiber members the translation restricts to a permutation of the fiber
(`UnfoldLab.tbWeight_gaugeCell`); in general it moves the distribution off the
fiber altogether.

The important part is what *survives*: the norm is unchanged, so the fiber sum
rule still holds exactly.  The translated fiber is still a complete set of
characters, and Parseval does not care which one.  **Neither of the package's
runtime sum-rule checks can detect this mistake.**  That is precisely why it
deserves a module of its own.

`tests/test_convention.py` shows the symptom end to end on the perfect chain:
read correctly, each band of a three-cell supercell carries weight one at a
single primitive k-point whose energy is `2 t cos(2 pi k)`; read as
full-wavefunction amplitudes, the same bands still sum to one over the fiber but
are smeared across all three of its members, with the maximum on the wrong one
once the shift exceeds half the fiber spacing.

### 23.3 The non-orthogonal twist

In an LCAO basis the per-orbital phase stops being free: the overlap kernel must
be regauged with the state, `S -> diag(u) S diag(u)*`
(`UnfoldLab.ovWeight_gauge`, `gauge_overlap_kernel`).  Forget it and the
*off-diagonal* of the numerator — the part that exists only because the basis is
non-orthogonal — is rotated;
`UnfoldLab.ovNumer_gaugeOrbital_untransformed` is the exact expression.  The
orthonormal case is the special case in which the regauging does nothing
(`UnfoldLab.IsOrthonormalOn.gaugeKernel`), which is the formal reason the
convention is invisible there.

## 24. Twenty-second pass — strained and approximately commensurate supercells

All four gates were clean on arrival (634 tests, `ruff`, `mypy`, and a Lean
build with no `sorry` and no warnings, every module reachable from `Main.lean`),
so this pass went looking for a gap rather than a regression.

### 24.1 The gap: "no" was the only answer

Every statement in the package assumes an exact `A_sc = T A_pc` with `T`
integer, and `detect_transformation` enforces it with a hard error whenever the
entrywise rounding residual exceeds `atol`.  That is correct — but it is also
the *only* thing the package had to say about a mismatch, and the mismatch is
common:

* a defect supercell whose cell parameters were relaxed;
* a heterostructure in which one layer is strained onto the other;
* a twisted stack replaced by a commensurate approximant;
* a supercell and a reference taken from two different calculations, or from a
  database, with slightly different equilibrium lattice constants.

A user hitting that error learns nothing about *how far off* the pair is, and
the natural next move — loosening `atol` — is exactly the wrong one, because
`check_atol` (rightly) refuses anything at or above `0.5` and anything below it
still gives no idea of the consequence.

### 24.2 Commensurability has no approximate version

`UnfoldLab.latticeSpan_subset_iff_intMatrix` settles the question of principle:
the supercell translations are primitive translations *if and only if*
`M = A_sc A_pc⁻¹` is an integer matrix.  There is no "almost a sublattice".  So
an incommensurate pair does not merely make the folding map inaccurate, it makes
it undefined: the supercell is not a union of whole primitive cells, and the
`|det T|` primitive k-points of a fiber are not the fold of anything.

`UnfoldLab.round_matrix_optimal` — entrywise rounding minimizes the residual over
all integer matrices, with `abs_sub_round_le_half` capping it at `1/2` — says
the residual reported by `detect_transformation` is not an artefact of a poor
choice: no integer matrix does better.  A residual near `1/2` therefore means
the transform itself is a guess, which the report flags as `ambiguous`.

### 24.3 What residual strain costs, quantitatively

Write the true supercell as the ideal one deformed by a Cartesian deformation
gradient `D`, `A_sc = (T A_pc) Dᵀ`.  Unfolding proceeds with the integer `T` and
reports the primitive fractional coordinate `k = T⁻¹ K`, whose Cartesian image
is taken against the *unstrained* reference.  Then
(`UnfoldLab.reciprocalLattice_deform`, `UnfoldLab.cartesian_strain_shift`) the
point the strained cell actually describes is that image times `D⁻¹`, so the
error is

    Δq = q (1 − D⁻¹)      (`UnfoldLab.strain_kshift`)

— **linear in k**.  Two consequences worth stating plainly:

* it is exactly zero at Γ, so a Γ-point check can never reveal it, and it is
  largest at the zone boundary, so it distorts a band path progressively along
  its length instead of shifting it rigidly;
* it does not go away.  `UnfoldLab.strain_kshift_eq_zero_iff` shows the
  assignment is correct at every k-point only when `D = 1`; picking a different
  integer transform changes which `D` one gets, but never removes it.

For a 1% lattice mismatch the error at a zone corner is about 1% of `|k|` — of
the same order as the k-spacing of a typical mesh, so it is not always
negligible, and it is systematic rather than random.

The report also separates a *rigid rotation* from a *strain* by polar
decomposition.  A rotated supercell is incommensurate too, and it still
misplaces k (it rotates every reported direction, so a band path expressed in
the reference frame no longer points where it did), but the cure is different:
rotate the reference, do not re-relax it.  The infinitesimal strain
`(D + Dᵀ)/2 − I` reports a spurious second-order strain for a pure rotation,
which is why `strain_tensor(..., kind="green-lagrange")` — exactly zero under
any rotation — is offered alongside it.

## 25. Twenty-third pass — quoting numbers from a spectral function

### 25.1 The gap: the package produced a picture, not numbers

`unfold` writes an `EffectiveBandStructure` and `plot_spectral` draws it, but
nothing in the package turned `A(k, E)` back into the quantities a paper
quotes: a band energy, a gap, a band velocity, an effective mass.  Users do
that by eye off the plot, or with an ad-hoc script — and the two steps involved,
peak finding and differentiation, both have systematic errors that a script
written by eye will not respect.

### 25.2 What is now proved

* **Peak refinement.**  A peak is located on the energy grid and refined on the
  parabola through the maximal sample and its neighbours.
  `UnfoldLab.parabolic_vertex_exact` shows the refinement returns the vertex
  *exactly* when the peak is locally quadratic, for any offset of the grid — so
  the sub-grid accuracy claimed by `spectral_peaks` is real, not folklore.
* **Curvature.**  `UnfoldLab.central_second_difference_cubic` shows the
  symmetric second difference reproduces the second derivative of any *cubic*
  exactly.  Not merely the quadratic term: the cubic term cancels by symmetry,
  which is why the effective mass is quartically accurate in the k-spacing and
  why a one-sided stencil — which is only linearly accurate — must not be used
  at the ends of a path.  `band_extremum` therefore refuses to report a mass at
  a path end rather than reaching for a one-sided estimate.
* **Resolution.**  The physically important one.  For two Gaussians of width
  `sigma` separated by `2d`, `UnfoldLab.gaussPair_merged` proves that for
  `d ≤ sigma` the broadened curve is *higher between the two states than at
  either of them*: what a peak finder reports is one peak, at an energy where
  no state exists.  `UnfoldLab.gaussPair_resolved` proves that at `d ≥ 2 sigma`
  each state outranks the midpoint, so the pair is genuinely two peaks.  The
  broadening width is thus a hard resolution limit with a proved sandwich
  around it, and `unresolvable_pairs` reports every place a peak table is about
  to claim more than the broadening allows.

The third point is the one that matters for unfolding specifically: an unfolded
spectrum is *dense* — a fiber contributes `|det T|` states to every k-point —
so nearly-degenerate pairs are the rule, not the exception, and a peak
dispersion read off a broadened map silently interpolates between them.

## 26. Twenty-fourth pass — conditioning of the overlap matrix

### 26.1 The gap

Pass 19 added non-orthogonal (LCAO) unfolding: weights `c* S K c / c* S c` and a
generalized eigensolver based on a Cholesky factorization of `S`.  Both steps
silently assume `S` is positive definite, and the code did nothing to check it.

That assumption is the one an LCAO calculation is most likely to violate.  A
basis with diffuse functions on neighbouring atoms is close to linearly
dependent; `S` acquires eigenvalues at rounding-error level; and then

* `numpy.linalg.cholesky` raises `LinAlgError`, and the caller saw only
  "matrix is not positive definite" with no indication of how badly, or what to
  do about it; and
* even where the factorization succeeds, a near-null coefficient vector has an
  `S`-norm dominated by rounding error, so the weight is a ratio of two
  quantities that are both noise.

Neither failure mode was diagnosable from the package.

### 26.2 What the formal side settles

`lean-proofs/RequestProject/Unfolding/Conditioning.lean`:

* `standard_of_generalized` / `generalized_of_standard` — for *any* `X` with
  `Xᴴ S X = 1`, solutions of `(Xᴴ H X) y = E y` and of `H c = E S c` with
  `c = X y` correspond.  Cholesky and canonical orthogonalization are two
  choices of the same `X`, so switching between them changes nothing about the
  answer where both apply.  (The converse direction carries the hypothesis
  that `Xᴴ` is invertible, i.e. that nothing was truncated.  When `X` *is*
  truncated only the projected statement survives — the residual
  `H c − E S c` vanishes against the retained subspace, not identically — and
  `tests/test_conditioning.py` checks exactly that weaker form.)
* `isHermitian_congr` — the transformed Hamiltonian stays Hermitian: the
  energies stay real and `eigh` is the correct routine, not `eig`.
* `sNorm_transformed` — a normalized `y` pulls back to a state with `c* S c = 1`,
  so the unfolding weight's denominator is one by construction.
* `sNorm_eq_zero_of_mulVec_eq_zero` — a null direction of `S` has zero `S`-norm.
  It is not a state; the correct response is to project it out, not to
  normalize it.
* `sNorm_ge_of_diagonally_dominant` — the useful one.  For a Hermitian `S` with
  unit diagonal whose off-diagonal row sums are at most `r`,
  `c* S c ≥ (1 − r) ‖c‖²`.  This is a Gershgorin-style bound proved directly
  from the sum, and it certifies positive definiteness in `O(n²)` — cheaper
  than the `O(n³)` factorization it replaces, and it also supplies a lower
  bound on the smallest eigenvalue.

### 26.3 What was added

* `unfoldlab/core/conditioning.py`: `hermitian_part` (symmetrize away the
  rounding asymmetry before any eigenvalue is taken), `diagonal_dominance_bound`
  (the cheap certificate, applied to the unit-diagonal scaling `D^-1/2 S D^-1/2`

  directions below threshold), `canonical_orthogonalization` and
  `solve_generalized_eigenproblem_truncated`.
* `unfoldlab.core.lcao.solve_generalized_eigenproblem` gained a keyword-only
  `threshold`, which delegates to the truncated solver; its Cholesky-failure

* `unfoldlab overlap --overlap S.npy [--hamiltonian H.npy] [--threshold ...]`.
* `tests/test_conditioning.py`, 23 tests.

### 26.4 Two deliberate limitations

*The dominance criterion is sufficient, never necessary.*  A chain overlap with
nearest-neighbour element `0.6` has row sum `1.2` and so a negative bound, while
its smallest eigenvalue is about `0.03`: positive definite, uncertified.  The
report says which of the two situations it is in
(`OverlapConditioning.certified_by_dominance`) rather than pretending the cheap
test is conclusive.

*Truncation is not threaded through path or model unfolding.*
`unfold_lcao_path` preallocates an `n_states` array, and a truncated solve
returns fewer states than basis functions — and a different number at different
k-points, so the result is not a rectangular band structure at all.  Rather than
silently padding, the truncated solver stays a diagnostic-level entry point; the
path functions keep requiring an `S` that is genuinely positive definite, which
`unfoldlab overlap` now lets one check in advance.

## 27. Twenty-fifth pass — the Fermi level and the energy reference

### 27.1 The gap

`core/windows.py` could integrate the unfolded weight below a given energy
(`band_filling`), but nothing in the package could *find* that energy.  The
Fermi level was an input the user had to supply from elsewhere, and three
things could go wrong without any of them being detectable:

1. **The count is per primitive cell, the calculation is per supercell.**  An
   unfolded band structure lives in the primitive zone; its electron count is
   the supercell one divided by `|det T|`.  Using the supercell number puts the
   level far above the true one.
2. **A band path is not a Brillouin-zone sample.**  Summing occupations over the
   k-points of a high-symmetry path, with or without weights, is not an
   integral over the zone, and the number it gives is not an electron count.
3. **A misreferenced run looks completely normal.**  A rigid shift of the energy
   axis changes every gap edge, every Fermi-surface cut and every occupied
   weight, and leaves no visible trace in the plot.

### 27.2 What the formal side settles

`lean-proofs/RequestProject/Unfolding/Fermi.lean` works with the occupied weight
`filling w e T E = ∑ w i · fermiDirac ((e i − E) / T)`.

* `filling_strictMono`, `tendsto_filling_atBot`, `tendsto_filling_atTop` — the
  count increases strictly and sweeps `(0, ∑ w)` as the chemical potential
  sweeps the real line.  These are what make a bracket exist and the expansion
  loop terminate.
* `existsUnique_fermiLevel` — for `0 < N < ∑ w` there is **exactly one** Fermi
  level.  The bisection is therefore converging to a well-defined number, and a
  count outside that interval has no solution at all — which is why
  `find_fermi_level` raises instead of returning an extreme energy.
* `filling_shift` and `fermiLevel_shift` — shifting every eigenvalue by `d`
  shifts the Fermi level by exactly `d` and changes no occupation.  This is the
  precise statement that a misreferenced run is wrong by a rigid shift and by
  nothing else, and it is what licenses `align_reference` to move the reference
  rather than the energies.
* `filling_add_empty` — occupied and empty weights add to the total, from the
  particle–hole symmetry `fermiDirac x + fermiDirac (-x) = 1`.
* `abs_filling_sub_le` — the count is Lipschitz with constant `(∑ w) / (4 T)`,
  proved from the `1/4` bound on the slope of the Fermi function.  Cold smearing
  makes the root sharper; the reciprocal is the energy error that a
  one-electron miscount can cause, and `FermiLevelReport.sensitivity` reports
  it.

### 27.3 What was added

* `unfoldlab/core/fermi.py`: `fermi_dirac_occupation` (evaluated as
  `exp(-x)/(1+exp(-x))` for `x ≥ 0`, which is the same number without the
  overflow the naive form produces above `x ≈ 709`), `state_occupations`,
  `total_weight`, `electron_count`, `electrons_per_primitive_cell`,
  `find_fermi_level` → `FermiLevelReport`, and `align_reference`.
* `unfoldlab fermi --input run.json --supercell-electrons N --multiplicity D`,
  with `--align` to write a copy of the run referenced to the level it found.
* `tests/test_fermi.py`, 20 tests.

### 27.4 The CLI split

`cli/diagnostics.py` had reached 834 lines and would have crossed the
1000-line limit `tests/test_cli_structure.py` enforces.  It is now two modules:
`cli/diagnostics.py` (505 lines) keeps the questions asked *about* an unfolded
run — `fiber`, `cut`, `ensemble`, `norms`, `degeneracy` — and the new
`cli/analysis.py` holds the commands that interrogate the inputs of a run or
extract physical numbers from a finished one: `detect-symmetry`, `strain`,
`dispersion`, `overlap`, `fermi`.  `cli/main.py` imports both, and the structure
test now pins `unfoldlab.cli.analysis` as a standalone-importable module.

### 27.5 A deliberate limitation

Only Fermi–Dirac smearing is offered.  Gaussian and Methfessel–Paxton
occupations are common in plane-wave codes, but their occupation functions are
error functions and Hermite polynomials, and the Methfessel–Paxton one is not
even monotone — the uniqueness theorem above is false for it.  Rather than ship
a solver whose root is not well defined, the module covers the case the formal
development covers and says so.

## 28. Twenty-sixth pass — the unfolded density of states

### 28.1 The gap

Every diagnostic the package had was local to one k-point: the fiber sum rule,
the stored-state norms, the weight bounds, the spin sum rule.  All of them are
statements *about the unfolding*, checked with quantities the unfolding itself
produced.  The package could not answer the one question that does not need the
unfolding at all — does the unfolded run still hold the right number of states?
— because it had no density of states.  `grep -ri dos unfoldlab/` returned
nothing.

That is a real gap and not a cosmetic one.  The supercell calculation has a
density of states fixed by its own eigenvalues, and unfolding may redistribute
spectral weight in k but must not create or destroy any.  Comparing the two
curves therefore tests the whole chain — reader, matching, weights, fiber
enumeration — against a reference that no part of that chain produced.

### 28.2 The mathematics

`lean-proofs/RequestProject/Unfolding/Dos.lean`.  For a complete fiber the weights of a band
sum to one (`IsFiberRepr.sum_weight_eq_one`), so summing the unfolded spectral
functions over the fiber returns the *undecomposed* spectrum of the supercell
k-point: `IsFiberRepr.fiberDos_eq_bandDos`, at every energy and for any
normalized kernel.  Averaged over the fiber — which is what counting per
primitive cell means, the `|det T|` members sharing the zone weight of the
supercell k-point they came from — it is the supercell curve divided by
`|det T|` (`IsFiberRepr.fiberDos_div_card`, using
`IsFiberRepr.card_eq_natAbs_det`).  Integrating, `integral_bandDos` and
`IsFiberRepr.integral_fiberDos` give the band count, so the unfolded curve
carries `n_bands / |det T|` states per primitive cell whatever the broadening.

Two weaker statements are the ones that survive an imperfect sample, and they
are what the diagnostic actually reports:

* `IsFiberRepr.fiberDos_subset_le` — an incomplete fiber, which is what a band
  path samples, can only *undercount*;
* `meshDos_le` — weights in `[0, 1]` cannot make the unfolded curve exceed the
  unweighted one, whatever the k-point sample.  This is the check that is
  meaningful on a path, and a violation is a bug rather than a coarse mesh.

The distinction matters and cost a rewrite of the report: the first draft
compared `|det T|` times the unfolded curve with the supercell curve and called
any excess a fault.  On an incomplete fiber that comparison is positive on both
sides and means nothing, because the retained members carry more than their
`1/|det T|` share of the sample.  The report now separates `max_excess` (the
weight bound, always valid) from `max_fiber_excess` / `max_fiber_deficit` (the
equality, valid only on a mesh of complete fibers).

### 28.3 What was added

* `unfoldlab/core/dos.py`: `unfolded_dos`, `supercell_dos`,
  `default_energy_grid`, the `DensityOfStates` container and
  `diagnose_dos_conservation` → `DosConservation`.  The running state count is
  evaluated in closed form (an error function for the Gaussian kernel, an
  arctangent for the Lorentzian) exactly as the energy windows are, so it does
  not depend on the resolution of the grid, and the total is computed from the
  weights rather than read off the last grid point.  `DensityOfStates.tail_loss`
  is the difference: negligible for a Gaussian at the default padding of five
  widths, of order a percent for a Lorentzian, whose tail is algebraic.
* `unfoldlab dos --input run.json --broadening w --multiplicity D`, with
  `--kpoint-weights`, `--emin/--emax/--points`, `--out` for the four-column
  table and `--json` for the report.
* `tests/test_dos.py`, 15 tests, including an end-to-end case: a four-site
  supercell of a chain with an on-site defect, diagonalized and unfolded over a
  uniform mesh, whose density of states is conserved to `1e-12` even though the
  defect has scattered the weight across the fiber.

### 28.4 Two shared helpers

`_normalized_kpoint_weights` was private to `core/fermi.py` and is now

## 29. Twenty-seventh pass — tracking peaks into branches

### 29.1 The gap

Pass 23 gave the package a peak table: for each k-point, the maxima of
`A(k, ·)` with a parabolic refinement and a resolution limit.  What it did not
give is the step everyone takes next — joining those peaks into *branches*, the
lines that get plotted and that a velocity or an effective mass is read off.
`effective_mass` took a band index and an array; on an unfolded spectral
function there is no band index, only peaks, and nothing in the package said
which peak at one k-point continues which at the next.

### 29.2 The mathematics

`lean-proofs/RequestProject/Unfolding/Tracking.lean`.  Score a pairing by the total squared
energy jump, `matchCost`.  Expanding the square leaves a cross term, and the
rearrangement inequality says two increasing lists maximize it: hence
`matchCost_id_le`, for peak lists in increasing order the order-preserving
pairing is optimal among *all* permutations.  There is therefore no assignment
problem to solve — sorting the peaks by energy *is* the algorithm — and any
matching that crosses can be straightened without cost.

Two negative statements matter as much:

* `matchCost_greedy_gt` — the cheap alternative of walking the peaks in order
  and giving each its nearest free partner is strictly worse on an explicit
  example (`36.01` against `25.81`).  Nearest-neighbour tracking is not a
  different convention, it is a worse answer by the measure that chose it.
* `exists_matchCost_tie` — where two peaks of a k-point coincide, two different
  matchings cost exactly the same.  The branch labels are then not determined by
  the energies at all: a crossing and an anticrossing are indistinguishable from
  a peak table, whatever rule is applied.  The only honest thing a tracker can
  do is report the k-point.

`abs_pair_exchange` is the same exchange inequality for the absolute cost, the
two-branch statement behind "sorted lines do not cross".

### 29.3 What was added

* `unfoldlab/core/tracking.py`: `track_branches` (a peak table plus the number
  of k-points), `track_spectral_peaks` (peak finding and tracking in one step),
  and the `Branch` / `Crossing` / `BranchTracking` containers.  Where the two
  k-points hold different numbers of peaks the alignment is the
  order-preserving one of least cost with a penalty per unmatched peak,
  computed by a small dynamic program; with equal counts it reduces to the
  sorted matching the theorem covers.  `max_jump` ends a branch at a step
  larger than itself, and `min_length` drops the stray peaks that are not
  bands.
* Ambiguities are reported, not resolved: a `Crossing` of kind `"degenerate"`
  where two peaks lie within the broadening, and of kind `"terminus"` where a
  branch begins or ends inside the path.  The second is needed because two
  peaks that have *merged* are no longer two peaks, so a separation tolerance
  alone would miss exactly the k-point where the ambiguity is worst.
* `unfoldlab branches --input run.json --broadening w`, with `--max-jump`,
  `--min-length`, `--min-intensity`, an energy range, a column-per-branch table
  and a JSON report.
* `tests/test_tracking.py`, 14 tests, including an exhaustive check of
  `matchCost_id_le` against all `5!` permutations of random ordered lists and
  the crossing case where the tracker follows the envelopes and says so.

## 30. Twenty-eighth pass — slabs, wires and partial periodicity

### 30.1 The gap

Every unfolding path in the package assumed all three cell directions are real
periods.  Most published unfolding is done on slabs: a surface reconstruction, a
2D alloy, an interface.  Such a cell is periodic in two directions and holds
vacuum in the third, and the third cell length is a convergence parameter — a
number the user increases until the energy stops changing.  Nothing in the
package said so, with two concrete consequences.

*A transform that folds along the vacuum direction was accepted.*  It is easy to
write one by accident: `detect_transformation` compares lattices, and a slab
built with twice the vacuum of the reference gives `T = diag(n, n, 2)` with no
complaint.  Unfolding then splits every state between `k_perp = 0` and
`k_perp = 1/2`, and the split is a function of the vacuum thickness alone.

*The perpendicular plane-wave index was carried through the matching test.*  A
converged slab has a long vacuum axis, hence a fine reciprocal spacing along it,
hence many `G` per parallel vector — often the largest factor in the plane-wave
list.  Every one of them went through the exact integer divisibility test
separately.

### 30.2 What the mathematics says

`lean-proofs/RequestProject/Unfolding/Slab.lean` fixes a non-periodic axis `p` and defines
`IsSlabTransform`: row `p` and column `p` of `T` are the unit vector `e_p`.

* `IsSlabTransform.foldsTo_perp` — the fiber of a slab transform is *flat*.
  Every primitive k-point folding onto `K` has the same perpendicular component
  as `K`, up to an integer.  There is nothing to unfold along the vacuum
  direction, and a path that disperses along it is asking for weights that are
  identically zero.
* `IsSlabTransform.pwMatches_perp_free` — the matching test never reads the
  perpendicular component of `G`.  Two stored plane waves differing only there
  are matched or rejected together.
* `IsSlabTransform.weight_perp_gauge` — hence the weight depends on the stored
  coefficients only through their totals at fixed parallel `G`.  Summing
  `|c_G|²` over the perpendicular index first is *exact*.
* `weight_vacuum_fold_half` and `weight_vacuum_fold_zero` — the pitfall in its
  smallest form.  In one dimension with `T = (2)`, the single plane wave `G = 1`
  receives weight one at `k = 1/2` and weight zero at `k = 0`.  The spurious
  assignment is not a tie that averaging would repair; it is a definite band
  whose only parameter is the length of the vacuum.

### 30.3 What was added

* `unfoldlab/core/slab.py`: `vacuum_gap` (largest empty stretch along an axis,
  measured cyclically along the outward normal, so a slab straddling the cell
  boundary is handled), `detect_vacuum_axes`, `is_slab_transform`,
  `embed_parallel_transform` (build a valid 3×3 transform from a 2×2 one),
  `flat_kpoint_deviation`, `diagnose_slab_transform` → `SlabReport` (folding
  factors, mixed axes, and the number of perpendicular k-points that are
  artifacts), `collapse_perpendicular` and `slab_weights_from_coefficients`.
* The collapse is the optimization the third theorem licenses: the integer
  matching test runs once per *parallel* G-vector instead of once per stored
  plane wave.  `slab_weights_from_coefficients` refuses a transform that is not
  trivial along the non-periodic axes — collapsing would then change the answer,
  and the answer it would change is itself an artifact.
* CLI `unfoldlab slab --structure POSCAR --matrix "..."`, which reports the gap
  along each axis, which axes it is treating as non-periodic (`--axis` to state
  them, `--vacuum` to set the threshold), and the verdict on the transform.
* `tests/test_slab.py`, 22 tests, including the exactness of the collapse
  against the ordinary kernel, the fiber sum rule on the collapsed list, and the
  three-dimensional form of the vacuum-folding pitfall.

### 30.4 What is still open

The diagnosis is geometric.  A slab whose two surfaces differ (an asymmetric
slab, or one with an adsorbate on one side) unfolds onto the *bulk* primitive
cell only in the interior; the surface layers have no reference at all, and the
weights they carry are not comparable with the bulk ones.  Nothing here detects
that, and a layer-resolved unfolding — `core/site_projection.py` already assigns
layers — would be the natural next step.

## 31. Twenty-ninth pass — layer-resolved unfolding, and what it can claim

### 31.1 The gap

Pass 28 left an open item: a slab whose two surfaces differ unfolds onto the
bulk primitive cell only in its interior, and nothing in the package said how
much of an unfolded weight comes from which part of the slab.  The obvious fix
-- restrict the weight to a layer -- is easy to implement and easy to
misinterpret, so the question worth settling first was what such a number
actually means.

### 31.2 What the mathematics says

`lean-proofs/RequestProject/Unfolding/Layers.lean` writes both splits as operators on the
coefficient vector: the k-point split is a partition of the plane-wave index,
the layer split is an operator `A` that is diagonal in *real space* and hence a
full matrix in the plane-wave basis.

* `sum_regionCharge_layers` — **at a fixed k-point the layer split is exact.**  If
  the layer operators add up to the identity, which any partition of space does,
  the layer charges of the matched component add up to the matched norm.  The
  layer decomposition of an unfolded weight is therefore a genuine decomposition
  at every k-point, with no assumption on where the boundaries are put.
* `regionCharge_eq_blockSum_add_crossForm` — **across k-points it is not.**  The
  charge a state carries in a region is the sum of the per-k-point charges plus
  a cross term between the k-point blocks.  Summing a layer's weight over a
  fiber does not return the charge of the layer.
* `crossForm_eq_zero_of_diagonal` and `sum_regionCharge_blocks_of_diagonal` — the
  cross term vanishes exactly when the region operator is diagonal in the same
  basis as the matching.  That is the case of a site or orbital projection in a
  tight-binding or LCAO basis, and is the reason
  `tight_binding_orbital_weights` carries a fiber sum rule
  (`sum_tbOrbitalWeight_eq_norm_share`) while a plane-wave layer charge cannot.
* `regionCharge_blockSum_lt` — an explicit two-dimensional region for which the
  per-k-point charges recover exactly half of the true charge.  The gap is not a
  small correction, and no choice of layer boundaries removes it.

### 31.3 What was added

* `unfoldlab/core/layers.py`.  The planar-averaged density is built from its
  Fourier coefficients, `rho_m = sum_{G_par, G_z} conj(c[G_par, G_z])
  c[G_par, G_z + m]`, so a layer charge is a *closed-form* integral of the
  density over the region and not a sum over a real-space mesh: no grid, and no
  discretization error at the boundaries.  `density_fourier_coefficients`,
  `planar_average_density` (for plotting), `layer_charges`,
  `layer_edges_from_structure` (boundaries midway between the atomic planes
  found by `detect_layers`), `layer_resolved_weights`, and
  `diagnose_layer_conservation` → `LayerConservation`, which reports the cross
  term explicitly.
* CLI `unfoldlab layers --wavecar WAVECAR --matrix "..." --edges "..."`, which
  reads one k-point of a WAVECAR, builds its fiber, and prints the layer weights
  summed over the fiber next to the discrepancy against the layer charges.
* `tests/test_layers.py`, 14 tests: the density is nonnegative and integrates to
  the norm, a Gaussian state built in the lower half of the cell is found there
  to better than a percent, the layer shares add up to the weight at fixed k,
  the k-summed shares miss the charge by a measurable amount, and the identity
  region (one boundary, one layer) has no cross term at all.

## 32. Thirtieth pass — Brillouin-zone meshes, and which k-points a run can resolve

### 32.1 The gap

Passes 25 and 26 added the two diagnostics that integrate over the Brillouin
zone: the Fermi level (`core/fermi.py`) and the density of states
(`core/dos.py`).  Both take a *mesh* of supercell k-points, and both are the
point at which a user stops thinking about a band path and starts thinking
about a sample of the zone.  Neither the code nor the formal model said
anything about that sample.  The package could fold a k-point, enumerate the
fiber above one supercell k-point (`fiber_kpoints`) and check whether a
requested k-point was in a list (`match_kpoints_modulo_lattice`), but it could
not answer the question a mesh run actually raises:

> I ran the supercell on an `n1 x n2 x n3` mesh.  Which primitive k-points can I
> unfold onto, and is the one I want among them?

Left unanswered, the failure mode is quiet.  A requested k-point that the mesh
does not carry is either an error from `match_kpoints_modulo_lattice` with no
suggestion of what *is* available, or -- worse, in a hand-rolled script -- the
nearest stored k-point, silently, with the band plotted at the wrong place.

### 32.2 What the mathematics says — `Unfolding/Mesh.lean`

A generalized regular mesh is generated by an integer matrix `M` and a
fractional shift `s`: the k-points with `M k = m + s`.  `M = diag(n)`, `s = 0`
is the Gamma-centred Monkhorst--Pack mesh, and `s = (1/2, 1/2, 1/2)` the
half-shifted one, which is also the convention VASP uses for its `KPOINTS`
shift.

* `Mesh_eq_setOf_foldsTo` — **a mesh is a fiber**: the mesh generated by `M`
  with shift `s` is the set of k-points that `M` folds onto `s`.  Everything
  already proved about fibers applies verbatim; in particular a mesh has
  `|det M|` points and the same Smith-normal-form enumeration produces them, so
  no new construction was needed on the Python side either.
* `unfoldedMesh_eq` — **the unfolded mesh is the mesh of the product**: the
  primitive k-points that fold onto some point of the supercell mesh are
  exactly the points of the mesh generated by `M @ T`, *with the same shift*.
  That is the answer to the question above, and `card_unfoldedMesh_repr` counts
  them: `|det M| . |det T|`.
* `IsFiberRepr.mesh_fiber_complete` — the unfolded mesh contains every member of
  every fiber over the supercell mesh.  Unfolding a whole mesh is therefore the
  situation in which the weight sum rules are equalities and the diagnostics
  verify the run rather than bound it; a band path can only ever bound it.
* `zero_mem_Mesh_iff` — Gamma is a mesh point exactly when the shift is
  integral.  Since the folding leaves the shift untouched, **a half-shifted
  supercell mesh resolves no primitive k-point of the corresponding Gamma-centred
  mesh, whatever the transform is**.  Nothing can be plotted at Gamma from such
  a run, and no amount of choosing `T` repairs it.
* `zoneBoundary_mem_iff` — the zone-boundary point `1/2 e_i` is sampled exactly
  when the division along `i` is even.  An odd mesh never sees the zone
  boundary.
* `mesh_resolution_bound` — a k-point at half the mesh spacing is that far from
  every mesh point: `1 / (2 N_i)` is the resolution, and it is the error made by
  substituting the nearest available k-point for a requested one.
* `exists_unfoldedMesh_not_product` — the counterexample that makes the module
  worth having.  With `M = diag(2, 2)` and `T = [[1, 1], [0, 2]]` the unfolded
  mesh contains `(1/4, 1/4)` and `(0, 0)` but *not* `(1/4, 0)`.  A
  Monkhorst--Pack mesh is a product of one-dimensional meshes and is closed
  under exchanging components between its members; the unfolded mesh is not.
  **No triple of divisions describes the resolvable primitive k-points**, so
  they have to be enumerated.  The three-dimensional instance
  `M = diag(2, 2, 2)`, `T = [[1, 1, 0], [0, 2, 0], [0, 0, 1]]` has 16 points but
  4, 4 and 2 distinct values along the three axes — a product mesh with those
  divisions would have 32.

## 33. Thirty-first pass — twisted and multi-layer stacks

### 33.1 The gap

The twist area was the thinnest part of the package.  `twist/geometry.py` was
50 lines (`in_plane_twist_angle`, `assign_layers_by_axis`) and
`twist/problem.py` could load several references and unfold onto one of them,
but neither could answer the two questions a twisted-bilayer user starts from:

* **which twist angles are commensurate**, and how large is the cell?  A
  twisted bilayer only has a Brillouin zone at the discrete commensurate
  angles, so this is the question that decides whether the calculation is
  possible at all — and there was no way to ask it;
* **what does "unfolding a stack onto layer A" mean** when the stack has two
  equally legitimate primitive references?

### 33.2 What the mathematics says

`lean-proofs/RequestProject/Unfolding/Twist.lean` (pass 31, Lean side) settles it.

*A stack is two folding problems sharing one supercell.*
`IsCommensurateStack Ta Tb Aa Ab Am` bundles `Am = Ta Aa` and `Am = Tb Ab`, and
`IsCommensurateStack.det_relation` then fixes the two multiplicities by the cell
volumes: `|det Ta| |det Aa| = |det Tb| |det Ab|`.  For two layers with equal
cell area the multiplicities are equal; for graphene on hexagonal boron nitride
they are not, and the fibers over one and the same supercell k-point have
different sizes.

*The transfer between the two primitive zones is the identity in Cartesian
reciprocal space.*  `IsCommensurateStack.transfer_cartesian_eq`: the fractional
coordinates differ, the physical k-vector does not, and
`foldsTo_transferK` says the transferred point sits in the fiber of the same
supercell k-point.

*The pitfall.*  `IsCommensurateStack.sum_weight_both_layers`: a state of the
stack has total unfolding weight **one in layer A's zone and one in layer B's
zone**.  Both references carry a complete fiber, so the same electron is
counted once per layer.  Spectral weight in one layer's effective band structure
therefore says *nothing* about which layer the state lives on — a conclusion it
is very easy to draw from a plot and very wrong.

*The honest layer question needs a projected weight.*  `layerWeight` restricts
the numerator to a subset of the basis and keeps the full state norm in the
denominator; `IsFiberRepr.sum_layerWeight_eq_fraction` says its fiber sum is the
*fraction* of the state on that layer, and `layerWeight_eq_zero_of_support`
that a state avoiding a layer has no projected weight anywhere in the fiber.
This is exact only in a site basis: a real-space layer is not a diagonal subset
of the plane-wave basis (`Layers.lean`), so there is deliberately **no**
plane-wave "layer subset" kernel.

*The commensurate angles are the norm form of the Eisenstein integers.*  For a
hexagonal lattice, `hexVec_normSq`: `|m a1 + n a2|² = a² (m² - m n + n²)`.  So
`(m, n)` and `(n, m)` have the same length and one is a rotation of the other,
which gives (`cosAngle_hexVec_swap`)

    cos θ = (4 m n - m² - n²) / (2 (m² - m n + n²)),

and the cell holds `Q = m² - m n + n²` primitive cells of each layer
(`det_moireBasis`), the moiré basis being `moireBasis m n` for layer A and
`moireBasis n m` for layer B — equal determinants, as the volume relation
requires.  `(m, n) = (2, 3)` gives `Q = 7` and `cos θ = 11/14`, i.e. 38.21°,
which is `60° - 21.79°`: the classic twisted-bilayer-graphene cell.

### 33.3 Two subtleties the enumeration has to get right

* **Aligned pairs are not twists.**  `(1, 2)` gives `cos θ = 1/2`, exactly 60°,
  and a hexagonal lattice is invariant under a 60° rotation: the two layers
  coincide and there is no moiré at all.  Such pairs are dropped.
* **The same twist can be written in a needlessly larger cell.**  `(1, 3)` and
  `(2, 3)` are both the 21.79° stack in 7 cells, but so is `(1, 5)` — in *21*
  cells, a threefold-larger supercell of the same structure and a
  threefold-more-expensive calculation for nothing.  Entries are therefore keyed
  by the folded angle and only the smallest cell is kept.  With those two rules
  the enumeration reproduces the standard table exactly: 21.787° at 7 cells,
  27.796° at 13, 13.174° at 19, 17.897° at 31, 9.430° at 37, 7.341° at 61.

A third one is a convention trap.  Fractional k-points fold as `k_s = k_p @ T.T`
in the package's row convention, which is the column-vector `T *ᵥ k` of the Lean
development — so the transfer `Tb⁻¹ Ta` is `k_b = k_a @ (adj(Tb) @ Ta).T /
det Tb` and *not* `k_a @ Ta @ adj(Tb) / det Tb`.  The first implementation used
the second form; it round-trips perfectly and is still wrong, which the
Cartesian-invariance test caught and the round-trip test did not.  A round trip
is not a check of a coordinate transformation.

### 33.4 What was added

* `unfoldlab/twist/commensurate.py`.  `moire_cell_size`; `CommensurateTwist`
  and `hexagonal_commensurate_twists(max_index, *, include_aligned)` with the
  two filters above; `commensurate_stack_transforms(m, n)` returning the two
  layer transforms of equal determinant; `transfer_kpoint` with the exact
  integer adjugate; `diagnose_stack` → `StackReport` / `LayerStackInfo`, which
  runs the existing `diagnose_commensurability` once per layer (nothing
  re-derived) and adds the per-layer multiplicity and rotation, with the
  double-counting caveat printed in `summary()`; and `layer_projected_weights`,
  which wires layer labels into the tight-binding orbital-group kernel so that
  the layer question is asked in the basis where it has an exact answer.
* CLI `unfoldlab twist [--max-index 8] [--moire POSCAR --layer LABEL=POSCAR ...]
  [--json ...]`: the commensurate table, or the per-layer diagnosis.
* `tests/test_twist_commensurate.py`, 19 tests: the classic TBG table, the
  aligned/duplicate filters, equal determinants, the moiré cell built from one

  a commensurate and on an incommensurate pair, the layer weights partitioning
  the total, and both CLI modes.

## 34. Thirty-second pass — shadow bands, and reading an order parameter off them

### 34.1 The gap

The roadmap's theory chapters list "charge-density-wave, Peierls, Jahn–Teller
and reconstructed-supercell unfolding", and the package could *produce* those
pictures — a distorted supercell is just a supercell — but it could not say
anything about them.  The whole point of unfolding a weakly distorted cell is
that the distortion is visible as a faint replica of the primitive band, and
nothing in the package knew that a replica is what one is looking at, how faint
it should be, or what its faintness measures.

### 34.2 What the mathematics says

`lean-proofs/RequestProject/Unfolding/Perturbation.lean` solves the two-level problem that
underlies every one of those distortions: the perturbation mixes `|k⟩` and
`|k - Q⟩`, whose unperturbed energies are `m ± d`, through one matrix element
`v`.  The file *diagonalizes* the 2×2 Hamiltonian rather than positing the
answer: `mulVec_upperVector` and `mulVec_lowerVector` are the eigenvalue
equations, `upperVector_orthogonal` and `upperVector_normSq` the orthogonality
and the norm, and `upperWeight_eq_component` / `lowerWeight_eq_component`
identify the unfolded weights with the squared `|k⟩` components of those
eigenvectors.  From there:

* **the fiber sum rule** in its smallest nontrivial case,
  `upperWeight_add_lowerWeight`: main band and shadow share the primitive
  character of `|k⟩` and exhaust it, so the two intensities always add to one;
* **the shadow is second order in the perturbation**.  The exact form is
  `w = v² / (2R(R+d))` with `R = √(d²+v²)` (`lowerWeight_eq_sq_div`), squeezed
  between `v²/(2(d+|v|)(2d+|v|))` and `v²/(4d²)` (`lowerWeight_ge`,
  `lowerWeight_le_quadratic`).  Halving the order parameter divides the shadow
  intensity by four — which is why shadow bands are hard to see, and why their
  *intensity*, not their position, measures the distortion;
* **level repulsion** (`splitting_ge`): the splitting never falls below `2|v|`,
  with equality exactly at the unperturbed degeneracy, where the weight splits
  evenly (`upperWeight_at_degeneracy`).  At that point a crossing and an
  anticrossing carry identical weight, so nothing in the picture distinguishes
  them — the same warning `Tracking.lean` gives about peak tables;
* **only `|v|` enters** (`upperWeight_neg`): a phase on the matrix element is a
  gauge choice, so a complex coupling may be replaced by its modulus;
* **the inversion** (`abs_coupling_eq`, `detuning_eq`): from a measured pair,
  `|v| = ΔE √(w₊ w₋)` and `d = (ΔE/2)(w₊ - w₋)`.  Both the coupling and the two
  *unperturbed* primitive energies come back out of the unfolded picture in
  closed form.

### 34.3 What was implemented

`unfoldlab/core/perturbation.py`:

* `two_level_solution` — the exact energies and unfolded weights, vectorized
  over a path.  It is checked in the tests against `numpy.linalg.eigh` of the
  same Hamiltonian, so the closed form is not merely internally consistent.
  At the fully degenerate, uncoupled point the weights are not determined by
  the physics; the even split is returned, the only representative-independent
  choice, and this is documented rather than hidden;
* `shadow_weight_bounds` — the two proved bounds, with `inf` returned for the
  upper bound at `d = 0` rather than a clipped value, so a caller is never
  handed a bound that does not follow from the theorem;
* `shadow_band_structure` — the model prediction as an
  `EffectiveBandStructure`, for plotting next to a real run;
* `coupling_from_peaks` and `diagnose_shadow_bands` — the inversion, applied at
  every k-point of a finished run, and `unfoldlab shadow` on top of it.

### 34.4 The caveat that came out of the tests

`diagnose_shadow_bands` picks the pair by weight: the two strongest states at
each k-point.  That is a heuristic, not a theorem, and the first version of the
test suite caught it — a bright state that is *not* the shadow partner displaces
the real one, and the "residual weight" diagnostic does not reveal it, because
the intruder is inside the pair and the residual is therefore small.  The
`pair_fraction` then looks reassuring while the inversion is meaningless.

Two things follow, and both are in the code: `--window` restricts the search to
an energy window around the reference energy, which is how one isolates the pair
straddling a gap, and `coupling_estimate` excludes k-points whose pair holds
less than a configurable share of the weight.  The failure mode is pinned by
`test_a_bright_unrelated_state_is_picked_up_without_a_window`, so it stays
documented rather than becoming folklore.  The CLI also warns when the recovered
`|v|` scatters by more than 10% along the path: a single matrix element then
does not describe the perturbation, and no single number should be quoted.

## 35. Thirty-third pass — the augmentation module was never connected

### 35.1 The gap

A coverage run over the whole test suite showed one module at **0%**:
`unfoldlab/core/augmentation.py`, 102 statements, never imported.  It was not
exported from `unfoldlab` or `unfoldlab.core`, no test touched it, no CLI
command called it, and neither it nor the 355-line `Unfolding/Augmentation.lean`

`docs/findings.md`.  The mathematics had been formalized and the numerical code
written, and then the two were left disconnected — a whole pass of work that a
user of the package could not reach and that no gate would have noticed
breaking.

This is worth recording as a process finding, not just a defect: `ruff`, `mypy`
and a green test suite all pass happily on a module nothing imports.  Coverage
is what finds it, and it is now part of the review checklist.

### 35.2 What was connected

* the seven public names (`augmentation_fraction`, `weight_error_bound`,
  `structure_factor`, `is_fiber_block_diagonal`, `augmented_weights`,
  `diagnose_augmentation`, `AugmentationReport`) are exported from
  `unfoldlab.core` and `unfoldlab`;
* `tests/test_augmentation.py` checks the module against explicit matrices,
  and in particular checks the two claims that carry the physics: a
  fiber-block-diagonal augmentation leaves the fiber sum rule *intact* — so the
  diagnostic really is blind to the PAW error — and a cross term between fiber
  members breaks it, so the hypothesis of
  `IsFiberRepr.sum_augWeight_eq_one` is not decorative.  The structure factor
  is checked to be `|det T|` on the primitive reciprocal lattice, zero off it,
  and one everywhere for a single unreplicated site;
* `unfoldlab norms` now prints the PAW bound next to the truncation bound and
  writes it into its JSON report.  The two are different statements about the
  same file: `delta / (1 - delta)` bounds the error from plane waves *missing*
  from the expansion (`UnfoldLab.weight_truncation_bound`), while `delta`
  itself bounds it when the shortfall is augmentation charge
  (`UnfoldLab.abs_augWeight_sub_weight_le`) — the tighter and, for a PAW run,
  the applicable one.

### 35.3 A bug the tests turned up

`AugmentationReport.summary()` returned early on the "negligible" branch and

norms exceed one — a reader using a different normalization convention, which
is the one case here that indicates something actually wrong — was therefore
reported as "augmentation negligible" and nothing else.  Both branches now emit
the warning.

## 36. Thirty-fourth pass — the same wavefunction squared once per k-point

### 36.1 Where the time went

Profiling `weights_from_coefficients` on a realistic size — 64 bands, one
component, 200 000 G-vectors — put 0.124 s per call in forming
`re**2 + im**2` over the whole coefficient array and summing it, against
0.022 s for building the matching mask.  The squared moduli are the cost; the
integer matching test is an order of magnitude cheaper.

That matters because the squared moduli do not depend on the primitive
k-point.  Only the mask does.  And the whole point of unfolding is that one
supercell wavefunction serves *several* primitive k-points:

* a complete fiber unfolds `|det T|` primitive k-points from one supercell
  k-point, and
* a symmetry-reduced band path revisits an irreducible k-point once for every
  member of its star that the path passes through.

Both readers already knew this at the I/O level.  Since pass 12 the
symmetry-reduced paths group the requested rows by stored k-point so that each
wavefunction is *read* exactly once and only one stays resident.  But having
read it, they then handed the group to `compute_plane_wave_unfolding_weights`
one `PlaneWaveKPointData` at a time, and the dominant arithmetic was repeated
for every row of the group.  A 4x4x1 supercell path over an irreducible wedge
therefore paid for the same squaring a dozen times over.

### 36.2 The batched kernel

`core/plane_waves.shared_weights_from_coefficients` takes an
`(n_kpoints, 3)` array of primitive k-points against a single wavefunction.
It squares the coefficients once, contracts the component axis once, and lets
the k-points enter only through a single matrix product with the
`(n_g, n_kpoints)` matrix of masks — a `tensordot` in the component-resolved
case.  The result has shape `(n_kpoints, n_bands)`, or
`(n_kpoints, n_bands, n_components)`.

`weights_from_coefficients` is now literally the `n_kpoints == 1` case of it,
so there is exactly one implementation of the arithmetic and the two cannot
drift.  The two are not bit-for-bit identical across batch sizes — contracting
an `(n_g, 8)` mask matrix and an `(n_g, 1)` one take different BLAS paths — but
they agree to a few ulp, which is what `tests/test_shared_weights.py` asserts.

`core/unfolding.SharedWavefunctionGroup` is the streaming counterpart of
`PlaneWaveKPointData`: one folded supercell k-point, one G-vector list, one
coefficient array, and a *list* of primitive k-points.  It validates the same
shapes and offers `expand()`, the equivalent one-at-a-time stream, which is
what the tests compare against.  `compute_plane_wave_unfolding_weights_shared`
consumes a stream of groups and concatenates the rows in order, so it returns
exactly what `compute_plane_wave_unfolding_weights` returns for the
concatenated expansion.  It keeps the same band-count and component-count
checks, and the same "at least one k-point" error.

Both symmetry-reduced readers — `_compute_weights_from_wavecar_symmetry` in
`io/vasp_wfc.py` and `_compute_symmetry_reduced_weights` in `io/qe_wfc.py` —
now yield one group per stored k-point instead of one item per path point.
The grouping, the row permutation and the memory behaviour are unchanged; only
the arithmetic per group is.

The *aligned* WAVECAR path was deliberately left alone.  It requires the file
to hold exactly the k-points of the k-map in order, so every wavefunction there
already serves exactly one row and there is nothing to batch.

### 36.3 What it buys

64 bands, 200 000 G-vectors, an eight-point fiber: 2.37 s one k-point at a
time, 0.35 s batched — 6.8x — with a maximum difference in any weight of
`3e-16`.  The speedup is bounded by the size of the group, which is `|det T|`
for a fiber and the star size for a symmetry-reduced path, and it approaches
that bound because the mask is the cheap part.

### 36.4 Why there is no new Lean

Nothing here is a new mathematical claim.  The weight of a band at a primitive
k-point is a function of that band's coefficients and that k-point's mask
alone, which is the content of `UnfoldLab.bandWeights_flatten` in
`Chunking.lean` (blocking over bands or plane waves returns the unblocked
answer); batching over k-points is the same observation read along the other
axis, and the fiber sum rule the batched result satisfies is the already-proved
`UnfoldLab.IsFiberRepr.sum_weight_eq_one`.  The risk in a change like this is
not that the mathematics is wrong but that the array plumbing is, which is why
`tests/test_shared_weights.py` checks the kernel against a Python-loop
transcription of the definition — nested loops over k-point, band and
component, with an explicit `abs` — rather than against the vectorized
function it replaces.  Testing a rewrite against the thing it rewrote proves
only that the two agree.

## 37. Thirty-fifth pass — the figure nobody without matplotlib had seen

### 37.1 Two things wrong at once

`plot_unfolded` lived in `unfoldlab/io/qe.py`.  That is the Quantum ESPRESSO
text reader, and `unfoldlab/workflows/vasp.py` was importing its plotter out of
it — a backend-neutral drawing routine reached through a format-specific
module, which is the kind of dependency that quietly makes a reader impossible
to move or replace.

Worse, the half of it that matters most to a user was untested.
`matplotlib` sits in the optional `plot` extra; `plot_unfolded` catches the
`ImportError` and falls back to `plot_unfolded_svg`, which writes an SVG with
nothing but the standard library.  So the SVG renderer is not a curiosity — it
is *the* renderer for an install without the extra.  The coverage report put it
at zero: matplotlib is present in the development environment, so the fallback
branch was never taken, and no test called the fallback directly either.

### 37.2 What the untested renderer did

Two defects, both invisible on the toy data one would try by hand and both
certain on real data.

**Out-of-window states were drawn outside the axes.**  With `emin`/`emax` the
matplotlib path calls `set_ylim`, which clips.  The SVG path used the same
numbers only to define the linear map from energy to pixel, and then drew every
state through it.  A state ten eV outside a two-eV window landed thousands of
pixels above or below the plot rectangle — on the axis labels, on the title, or
off the canvas entirely.  Checked directly: energies `+-10 eV` with
`emin=-1, emax=1` put markers at `y = -2220` and `y = +2780` in a canvas whose
plot box is `y in [30, 530]`.  Since a band-structure figure is *usually*
windowed, most SVG outputs the code has ever produced were wrong in this way.

**One `nan` destroyed the whole figure.**  `y_min` came from
`np.min(energies - fermi)`, so a single non-finite entry — an unconverged band,
a missing eigenvalue, a placeholder — made the axis range `nan`, and every
coordinate in the file came out as `y="nan"`: the tick marks, the tick labels,
the zero line, every marker.  The output was an unopenable SVG rather than a
figure missing one point.

A third, milder inconsistency: matplotlib's `s` is a marker *area*, and the SVG
was using an affine function of the weight as a *radius*.  The two renderers
therefore gave visibly different pictures of the same data, with the SVG
exaggerating low weights.

### 37.3 What was done

The code is now `unfoldlab/io/plot_bands.py`, alongside the heat-map plotter
`io/plot_spectral.py` that a previous pass wrote properly (fallback included,
and tested).  It takes any object with a `distances` array — a `QEKMap`, an
`EffectiveBandStructure`, anything — expressed as a `Protocol`, so it has no
QE dependency and the VASP workflow no longer imports through one.  `io/qe.py`
re-exports the three names so existing code keeps working, and the module
docstring says why.

The renderer now:

* omits states outside `[emin, emax]` instead of drawing them outside the box;
* omits states with a non-finite energy or weight, and computes the automatic
  axis range from the finite entries only, so a `nan` costs one marker;
* validates that `energies` is two-dimensional, that `weights` has the same
  shape and that `distances` has one entry per k-point — the matplotlib path
  now checks this too, where it previously produced a scrambled figure from a
  mismatched `weights` array;
* draws a radius of `sqrt(3 + marker_scale * w)`, so the marker *area* is
  exactly matplotlib's `s` and the two pictures agree.

`marker_area` is a public function precisely so the two renderers can be seen
to share it.

`tests/test_plot_bands.py` (23 tests) covers both renderers, including the
fallback reached the way a user reaches it — by making `import matplotlib`
fail — and asserts the two repaired behaviours directly: every drawn marker
lies inside the plot rectangle when a window is given, and a figure containing
a `nan` energy has one marker fewer and no `nan` anywhere in the file.

### 37.4 The general lesson

This is the second module in three passes found by the coverage run rather than
by the four gates (the first was `core/augmentation.py` in pass 33).  Both were
invisible for the same reason: the tests were run in an environment where the
code path could not be taken.  A fallback for a missing optional dependency is
by construction dead code in a development environment that installs every
optional dependency, so it has to be called *directly* by a test, and the
dependency-missing branch has to be provoked deliberately.

## 38. Thirty-sixth pass — the symmetry operations nobody checked, and magnetism

### 38.1 The repository as received

The tree arrived flattened: every directory level had been dropped, so
`lean-proofs/RequestProject/Unfolding/*.lean`, `unfoldlab/core/*.py`, `tests/*.py`,
`docs/*.md` and `examples/*.json` all sat side by side in the root, the Lean
library `lean-proofs/RequestProject` had no files where the lakefile said it should, the
package `unfoldlab` did not exist as a package, and the root `README.md` had
been overwritten by the one pytest writes into its cache.  Build caches
(`.pytest_cache`, `.ruff_cache`, `.coverage`, `__pycache__`) were committed.

The layout was restored from the imports themselves — every module says where it
belongs — the caches were removed and ignored, and the README rewritten.  All
four gates then passed unchanged: 888 tests, `ruff`, `mypy`, and a `lake build`
of 8071 targets with no `sorry` and no warning.  Coverage was 90 %, with no
module at zero, so the pass-33 orphan check found nothing this time.

### 38.2 The gap: an unchecked hypothesis at the heart of symmetry reduction

Symmetry-reduced unfolding is the one place where the code uses a *stored*
wavefunction for a k-point it was not computed at.  `Symmetry.lean` proves the
geometry of it — the matching predicate and the weights are equivariant under
`S_pc` and `S_sc = T S_pc T⁻¹` — but the identity only says something about the
physical run if the wavefunction at the star member really is the symmetry image
of the stored one.  That is a fact about the *crystal*, and
`map_kpoints_to_stored` cannot see the crystal: it is handed a list of integer
matrices and checks that they are unimodular and that `T S T⁻¹` is integral,
i.e. that they are compatible with the two *lattices*.

Nothing downstream catches a wrong operation.  The weights it produces are the
weights of a real state — just not of the state that was asked for — so they lie
in `[0, 1]`, they obey the fiber sum rule, they obey the across-bands sum rule,
and they plot.  This is the worst class of error the project can have, and the
review had not previously named it.

Three new machine-checked statements in
`lean-proofs/RequestProject/Unfolding/SymmetryHypothesis.lean` pin it down:

* `weight_symmetry_of_norm_eq` restates the recipe with the hypothesis exposed.
  What is actually needed is weaker than `weight_symmetry` assumes: only that
  the star member's coefficients, read against the rotated plane-wave list, have
  the same *moduli* as the stored ones.  Any phase, and any gauge inside a
  degenerate multiplet, is invisible.
* `exists_weight_ne_of_coefficients` shows the hypothesis is load-bearing: with
  one transform, one k-point and one plane-wave list, one coefficient vector
  gives weight `1` and another gives weight `0`.  No geometric argument can
  supply the missing information.
* `exists_latticeSymmetry_bandEnergy_ne` is the pitfall in the form a user meets
  it.  For a square lattice with hoppings `t` along x and none along y, the
  exchange of the two axes is unimodular and commutes with every diagonal
  supercell transform — every test the code makes passes — and the two k-points
  it identifies, `(1/2, 0)` and `(0, 1/2)`, carry energies `-2 t` and `+2 t`.

### 38.3 The magnetic half of the same gap

`space_group_operations` decorated its sites with the species alone, so for a
spin-polarized run it returned the group of the nonmagnetic skeleton.  A
collinear calculation solves one Hamiltonian per spin channel, and a channel is
invariant only under the operations that leave the *moment pattern* alone: an
operation exchanging an up site with a down site maps the majority-spin problem
to the minority-spin problem.  `zeeman_invariant_iff_moment_invariant` is that
statement, and `exists_species_invariant_moment_not` the antiferromagnetic pair
that exhibits it.

`space_group_operations`, `detect_primitive_operations` and the new
`site_labels` now take `magmoms`:

* one number per site — the collinear case — decorates the sites, because spin
  and space are decoupled in a non-relativistic spin-polarized run;
* three numbers per site — the noncollinear case — is instead *rotated with the
  operation*, as the axial vector it is, `m -> det(R) R m`, using the new
  `cartesian_rotation`.  A ferromagnet along z in a cubic cell then keeps 8 of
  its 48 operations, which is the unitary part of `4/mm'm'`, and a moment along
  `[111]` keeps 6.

One thing worth recording, because it looks like a bug and is not: an
antiferromagnetic doubling loses half of its space-group *operations* to the
moments and yet keeps every *rotation*, each paired with a different
translation.  Since a translation only multiplies a coefficient by a phase and
the weights see `|c|²`, the operation list used for unfolding is correctly
unchanged.  A ferrimagnetic pattern — moments `1, 2, 3` on three sites of a
chain — does halve it, and that is the case the tests use.

### 38.4 What was done

* `validate_primitive_operations(structure, operations, transform, ...)` in
  `core/spacegroup.py` performs the missing check, reporting per operation
  whether it is even lattice-compatible (integral, unimodular, integral in
  supercell coordinates), whether it is a symmetry of the decorated supercell,
  and whether it is one only after adjoining `k -> -k`.
* `unfoldlab check-symmetry --structure ... --matrix ... --symmetry ops.txt
  [--magmom ...]` runs it from the command line and exits non-zero on a
  rejection.
* `unfoldlab detect-symmetry --magmom ...` restricts the detected group to the
  magnetic one, and refuses `--time-reversal` for a magnetic structure.
* `unfoldlab weights --structure ...` and `unfoldlab unfold --supercell ...`
  now validate a `--symmetry` file against the structure whenever one is
  supplied, and refuse to run with a message naming the offending matrices.
  Without moments the calculation is assumed nonmagnetic, so an operation that
  is a symmetry once `k -> -k` is adjoined is accepted; `--magmom` turns that
  off, because time reversal is not a symmetry of a magnet.
* `cli/analysis.py` had reached 1032 lines with the new command in it, over the
  1000-line limit `tests/test_cli_structure.py` pins, so the two symmetry
  commands moved to `cli/symmetry.py`.
* `tests/test_symmetry_validation.py` and `tests/test_symmetry_cli.py`, 21 tests
  in all.  The first of them checks the pitfall the way a user meets it: the
  kernel accepts the axis exchange of a tetragonal cell and serves one k-point's
  wavefunction for another, and the new validator rejects it.

### 38.5 The general lesson

A check that a routine *cannot* perform is not thereby someone else's problem.
`map_kpoints_to_stored` is right not to demand a structure, but the package as a
whole had a way to obtain one — the POSCAR was already being read for the
projection selectors — and never used it.  Where a hypothesis is unverifiable
locally, the place to verify it is wherever the missing input is available; if
that place exists, an honest docstring is not a substitute for the check.

## 39. Thirty-seventh pass — the matching mask, once instead of once per k-point

### 39.1 The observation

The weight of a primitive k-point is a sum of `|c_G|²` over the supercell plane
waves that unfold onto it.  Which ones those are is decided by
`matching_g_mask`, and the batched kernel introduced in pass 34 called it once
per primitive k-point, stacking the results into an `(n_g, n_kpoints)` matrix of
zeros and ones and contracting.  Two costs scale with the number of k-points
that way, and neither has to:

* the integer matching test itself — `as_int_array` on the whole `(n_g, 3)`
  array, the product with `adj(T).T`, and the modulo — is redone in full for
  every k-point, though only the *offset* `m₀ = K_sc - k_pc @ T.T` changes;
* the contraction against the dense mask matrix costs `n_bands · n_g ·
  n_kpoints` multiply-adds, though every column of the mask is orthogonal to
  every other: a plane wave matches *at most one* member of a fiber.

For a complete fiber `n_kpoints = |det T|`, so both carry a factor that a
2×2×2 supercell inflates eightfold and a 4×4×4 supercell sixty-fourfold.

### 39.2 The structure that removes it

Write the matching condition with an explicit folding witness: `G` matches `k`
exactly when `(G + m₀) @ adj(T).T ≡ 0 (mod det T)`.  Split it, and the
`G`-dependence and the `k`-dependence separate completely:

`clsLabel(G) = G @ adj(T).T mod |det T|`  matches  `-m₀ @ adj(T).T mod |det T|`.

The left-hand side does not mention the k-point.  It is a *class label*: by
`UnfoldLab.clsLabel_eq_iff_mem` two vectors share a label exactly when they
differ by a supercell lattice vector, so the labels name the `|det T|` classes
of `ℤ³ / T·ℤ³` faithfully and with no tolerance anywhere.  The matching test is
then the single integer comparison `UnfoldLab.pwMatches_iff_clsLabel_eq`, and
`UnfoldLab.clsLabel_eq_iff_congrModZ` says the label identifies the k-point just
as faithfully: two fiber members select the same class only if they are the same
point of the primitive zone.  Distinct k-points therefore collect disjoint sets
of plane waves, a repeated k-point is served twice from the same class, and
`UnfoldLab.sum_over_matching_eq_sum_over_class` turns the whole accumulation
into a segmented sum over the classes — one pass over the coefficient array for
*all* the k-points together, whatever their number.

### 39.3 What was done

* `lean-proofs/RequestProject/Unfolding/Classes.lean`, imported from `Main.lean`: the four
  statements above plus `clsLabel_add` and the filter identity
  `filter_pwMatches_eq_filter_clsLabel` that they rest on.
* `core/plane_waves.py`: `_g_class_residues`, `_kpoint_class_residues`,
  `_class_labels`, `_class_partition`, `_class_sums` and `_select_classes`.
  `shared_weights_from_coefficients` now labels the G-vectors once, sorts the
  labels once, sums each class once (`np.add.reduceat`), and lets each k-point
  look its class up — an absent class giving weight zero, which is the honest
  answer for a k-point no stored plane wave reaches.
* `compute_weights_from_coefficient_table` lost its loop over k-points and its
  two `np.add.at` calls: a row matches when its G-label agrees with its
  k-point's label, and both accumulations are single `np.bincount` calls.
* `tests/test_gvector_classes.py` (7 tests): a non-diagonal transform, a
  repeated k-point, an unoccupied class, an empty G list, the coefficient-table
  reader, and both labelling paths — the packed one and the sorted fallback used
  when `|det T|³` would overflow an `int64`, which is exercised both by
  monkeypatching the threshold and by a genuinely huge determinant.
* `examples/benchmark_weights.py` times the three routes and checks they agree.

### 39.4 The numbers

35 937 G-vectors, 60 bands, a 4×4×4 fiber of 64 k-points:

| route | time |
| --- | --- |
| one call per k-point | 2.150 s |
| dense mask matrix (pass 34) | 0.104 s |
| G-vector classes (now) | 0.035 s |

The weights are *bit-for-bit* identical along all three routes — the largest
disagreement printed by the benchmark is exactly `0`, since the same squared
moduli are added, only grouped differently.

### 39.5 What was measured and left alone

The tight-binding path was profiled in the same pass and deliberately not
touched.  For a 64-cell, 4-orbital supercell over 200 k-points,
`unfold_tight_binding_path` spends 3.54 s of 3.79 s inside `numpy.linalg.eigh`
and 0.04 s assembling the Bloch matrices; batching the assembly or the
diagonalization changes the total by under a percent, because the cost is
`(|det T| · n_orbitals)³` per k-point and lives in LAPACK.  The `np.add.at` in
`_assemble_supercell_hamiltonian` looks like a slow path and is one, but it is
0.2 % of the runtime.  Optimizing it would be work with no user-visible effect,
and the honest conclusion of a measurement is sometimes that the code is already
bound by a library call.

## 40. Pass 38 — which k-point is being reported: the first Brillouin zone

### 40.1 The gap

Every earlier pass treated a k-point as a point of the *torus*: the matching
kernel, the fiber enumeration and the sum rules all care only about the coset
`k + Z^3`, and the package's one reduction, `wrap_fractional` / `rint`, picks
the parallelepiped representative.  That is correct for the arithmetic and had
been formalized as such (`fold_congrModZ`).

It is not correct for anything *geometric*, and the package had no other
reduction: `rg -n "brillouin|wigner|first_bz"` over `unfoldlab/` returned
nothing.  Wherever a reduced fractional coordinate is quoted as "the k-point" —
a Fermi-surface or constant-energy cut, a valley centre, an unfolded mesh
listing, a plot axis — the parallelepiped representative can be well outside the
first Brillouin zone, because the parallelepiped is not the Wigner–Seitz cell of
a non-orthogonal lattice.  This is the reciprocal-space twin of the real-space
minimum-image bug found in pass 4 and recorded in `Pitfalls.lean`; that one was
fixed for *distances* only, by `minimum_image_distance`, which returns a length
and not a representative.

### 40.2 The mathematics

`lean-proofs/RequestProject/Unfolding/BrillouinZone.lean` (new, imported from `Main.lean`)
defines `IsBZRepr B f` — no lattice translate of `f` is shorter in Cartesian
length — and proves:

* `isBZRepr_iff_bragg`: the zone is the intersection of the half spaces
  `|2 ⟪k, g⟫| ≤ ‖g‖²`, one per reciprocal-lattice vector `g`.  Membership is a
  scan over lattice vectors, not a minimization;
* `isBZRepr_of_two_mul_lt`: a k-point closer to Γ than half the shortest lattice
  vector is in the zone, which is the cheap sufficient test;
* `bragg_eq_of_isBZRepr` and `eq_of_isBZRepr_of_strict`: two zone
  representatives of one coset have equal length and lie exactly on the Bragg
  plane of their difference, so away from the boundary the representative is
  unique — the ambiguity is real but confined to a measure-zero set;
* `isBZRepr_of_rounded_of_orthogonal`: for a lattice with mutually orthogonal
  basis vectors, componentwise rounding *is* the zone reduction.  So the naive
  code was right, exactly and only, for orthogonal cells;
* `exists_rounded_not_isBZRepr`: and wrong otherwise.  For the two-dimensional
  lattice with basis `(1, 0)`, `(1, 1)`, the fully rounded coordinate
  `(1/2, 1/2)` has a translate five times shorter in squared length;
* `isBZRepr_of_box_certificate`: the certified box search of
  `MinimumImage.lean` — the one the package already uses for distances —
  returns a genuine zone representative;
* `foldsTo_add_ivec`: reduction moves a k-point by a lattice vector, so no
  fiber, weight or sum rule changes.  The new representative is a reporting
  choice, not a change of physics.

### 40.3 The implementation

`unfoldlab/core/brillouin.py` (new):

* `reduce_to_first_bz` returns a `BZPoint` — the reduced fractional coordinate,
  the integer translation, the Cartesian vector, its length, and the length the
  rounded representative would have had, so the caller can see the discrepancy;
* `zone_boundary_distance` is the signed Cartesian distance to the nearest Bragg
  plane (positive inside, zero on the boundary, negative outside) and
  `is_in_first_bz` its sign.  The scan is certified the same way as the box
  search: the plane of `g` is at least `‖g‖/2 - ‖k‖` away, so the box grows
  until no outside vector can win;
* `shortest_lattice_vector_length` / `inscribed_radius`, also certified;
* `has_orthogonal_reciprocal_basis`, the scale-free test of the hypothesis of
  `isBZRepr_of_rounded_of_orthogonal`;
* `diagnose_bz_reduction`, which reports over a k-point list how many points
  rounding leaves outside the zone and by what factor the worst one is too long.

The minimum-image search in `core/valleys.py` was refactored rather than
duplicated: `certified_minimum_image_shift` now returns the winning translation
as well as the distance, and `minimum_image_distance` is a one-line wrapper, so
there is one certified search in the package and not two.  `_box_shifts` became
public as `box_shifts` for the same reason.

`unfoldlab bz` exposes all of it: `--point` and/or `--kpoints` (the TSV that
`unfoldlab mesh --kpoints` writes is accepted directly), `--structure` for the
reciprocal lattice, `--out` for the reduced list and `--json` for the report.
Without `--structure` it warns that the lengths are fractional norms, which are
the physical ones only for a cubic cell.  `unfoldlab mesh --kpoints ... --first-bz`
appends the zone representatives (`b1 b2 b3`) to the k-point listing, which is
the form a Fermi-surface or constant-energy plot of an unfolded mesh needs.
